The sidebar

The sidebar runs the full height of the editor, on the right of the canvas, with a row of tabs along its top. It is the same surface in all three editors, and it is where most of what Penstock adds to a diagram is read: the properties of what is selected, the scenarios of a process, what the check found, what the engine is doing, and the code behind a step.

The tabs

Each editor registers its own tabs, in a fixed order. The row shows them as icons when the sidebar is narrow, with a tooltip that names the tab, and a count badge on Problems. A tab with nothing to show keeps its place and says what it is for and what to do next.

DiagramProperties, Scenarios, Problems, Monitor, Code
DecisionProperties, Problems
FormProperties, Preview, Problems

The sidebar is a third of the width of the editor, between 320 and 480 pixels, and the dividing line can be dragged between 280 pixels and half the editor. The width and the tab you left selected are kept in ~/.penstock/preferences.json, so they are the same in every IDE on the machine. Below about 840 pixels wide the sidebar becomes a drawer over the canvas rather than a column beside it.

Problems, Monitor and Code each keep their own state while you look at another tab, so Monitor keeps the instances it fetched and Code keeps what you had open. The tabs choose the view; going deeper inside one is a separate thing, and a small ‹ in the tab's own header takes you back a step.

Properties

The properties panel of the selected element, the same one bpmn.io's properties panel draws, with the groups the engine profile defines. With nothing selected the tab is empty. See Editing a diagram.

In the decision editor it is the requirements diagram's properties: the id, name and documentation of a decision, and its version tag and history time to live on Camunda 7 and CIB seven, or its version tag alone on Camunda 8. Over a decision table the tab is empty on purpose, because a decision table belongs to its requirements diagram, and it offers an action that opens it. On Operaton it shows the id and the name and nothing else.

Scenarios

Scenarios is a process and the ways through it. A scenario is one way through: a start, a path of steps, the gateway conditions that decide the path, and the values the path needs. They are Camunda Process Test test cases, so they run under Camunda's own tooling as well as under Penstock. The tab reads the diagram's test-case file, and a diagram whose file has been renamed still finds it by the process id inside.

Pro, and Team in a pipeline. Without it the editor says what scenarios are and offers to buy them.

Generating scenarios from the diagram

Generate in the Scenarios panel does not write files. It opens a review over the diagram: the scenario you are looking at is drawn on the canvas with its steps numbered and the flows between them, and the steps are listed beside it in plain words, with the value each step passes on. A value can be edited, and a gateway condition that cannot be right is fixed from the step that holds it. Every change plans the scenarios again, so the drawing and the list always agree. Nothing reaches the file until you press Create scenarios.

A scenario already in the file is kept as it is, and its box is ticked and cannot be unticked, so generating never loses work. A way the process takes that the data cannot choose - a gateway whose conditions need something no variable can decide - is listed with a note saying so, and is not offered for writing.

The same view opens a saved scenario, so what a scenario does can be read before it is run. After a run the same view shows the plan against what actually happened, step by step.

Add scenario plans one scenario by hand, and for a process that starts on a message, a timer or a signal it asks which start event to begin from. The process instance is then started at that event directly, so the first steps of a process that waits for something are still covered. A start kind Penstock cannot express as a scenario is said in the review rather than left out quietly; penstock scenarios generate behaves the same.

Running scenarios

Run all runs the test cases against the engine the profile in force names, step by step, and stops at every step left to ask. A step can be answered by the real worker, or by a mock: complete it, throw a BPMN error, fail a number of times and then complete, or ask. A timer can be made to fire at once. Each step a mock answered carries a Mocked badge on the canvas, and the table under the run says what each step received, sent and changed, and where each value came from.

Every test case is checked against the Camunda test-case schema before the run starts. A case that lacks what the schema requires, such as an assertion with no processInstanceSelector or an instruction with a property the schema does not allow, is not run and says what it lacks.

A run never touches the definitions you deployed. It builds a copy whose ids are prefixed with penstock.<run>., every process, decision, form and the calls between them, deploys that, and removes it afterwards, so what is left on the engine is what you deployed and the process id you start is the one you deployed.

Test cases run against an engine marked deployment.forTests: true. A local engine is used once you have confirmed it, in the editor once per profile and in a terminal once per run; any other engine is refused, by the IDE as well as by the editor, and a pipeline never uses one without the mark. See Configuration.

Run with input… starts an ad-hoc run with start variables and a behaviour per step. Open a run… shows the path and the steps of an instance that already exists. Save as scenario… writes what was answered as a scenario that checks the path and the variables. The test-case file also runs in the IDE's own test runner, from the gutter of each case or of a folder.

Problems

The Problems tab is the full list of what the check found, in groups, with an error or warning icon on each finding. The check card over the canvas is a short summary of the same findings; the tab is where all of them are. See Check and problems.

Clicking a finding selects its element on the canvas and opens the property that fixes it, for job type, form key or id, correlation key, history time to live, called element, error, escalation, message and signal references and timer definitions, and a missing job type, topic, class or delegate expression in code. A finding with no single field still switches the sidebar to Properties and selects the element.

Monitor

Monitor asks the engine what it is doing with this diagram: the incidents it has, and the instances waiting at each step. The badges stay on the canvas as well, so a busy step is visible without opening the tab. The engine is asked when you open the tab or press Refresh, never in the background.

The header names the engine and the version of each process it found, which is how you know whether you are looking at what you think you are. A process that is not on the engine yet says so. An incident lists the message the engine gave, and Go to code opens the worker that runs the task, when the project has one. Clicking an incident selects the element.

Free. With no engine connected the tab says how to set one up and offers to open the connection, rather than showing an empty list. Camunda 7, Operaton and CIB seven are asked on their engine-rest address, and Camunda 8 from 8.8 and later.

Code

The Code tab shows the code behind the selected step: the workers, classes, beans, tests and usages that name it, with Go to code, Find usages, Run tests and Debug tests on the head of the tab. A group with more than a handful of entries is opened in a view of its own, with a ‹ back.

Pro, and Team in a pipeline, as part of the link between diagrams and code. Without it the tab says so and offers to buy it. See Plans and licence.

With nothing selected the tab says Select a task to see its code. A step nothing in the project runs, tests or uses is said plainly, rather than left as an empty tab.

Preview, in the form editor

Preview opens the form as a user sees it, beside the JSON it is given and the JSON it would submit. The input starts as sample data made from the fields themselves - a text, a number, the first option of a choice, one row of a dynamic list, a group under its path - and follows the form as you edit it until you write your own. When the JSON is not valid, the tab says what is wrong with it.

It is why the canvas never grows a fourth column for the preview. The toolbar's Preview button opens the same tab, and its tooltip says the palette is hidden while it is open. The form-js watermark stays visible.
