Validation

Validation answers whether a process is modelled correctly: an event with no outgoing flow, a gateway that splits without saying how, a service task with no job type. Penstock runs it without any setup, in the editor as you draw and in penstock check, with nothing to install and no paths to configure.

Which rules apply

Without a configuration the rules are bpmnlint's own recommended set, bpmnlint:recommended. A .bpmnlintrc in the project root replaces that set, and the editor and the command line both read it. To keep it somewhere else, name it with lint.configPath in penstock.yaml, relative to the project root; see Configuration.

A minimal .bpmnlintrc:

{
  "extends": ["bpmnlint:recommended"],
  "rules": {
    "label-required": "error",
    "no-implicit-split": "warn"
  }
}

Engine compatibility

Penstock also runs the rules of bpmnlint-plugin-camunda-compat, which ask what the engine the diagram is written for can actually run: a service task with no job type, an element or an expression the chosen Camunda version does not support, a process with no history time to live. They are free, and they are part of the same .bpmnlintrc.

They are checked against the version in the file's modeler:executionPlatformVersion, or the newest one when the file has none, and against the engine penstock.yaml names. Operaton and CIB seven are checked as Camunda 7.

Each compatibility rule has an id, such as compat/implementation, and its own page in the rules catalogue with a line on why it matters and a line on how to fix it. To turn one off, name it in .bpmnlintrc as camunda-compat/<rule>, the plugin's own name, or as compat/<rule>:

{
  "extends": ["bpmnlint:recommended"],
  "rules": {
    "camunda-compat/compatibility": "off"
  }
}

See Check and problems for what the findings look like and where they appear.

In the diagram editor

The editor marks problems on the elements as you draw, with a marker on each element a rule reports. The linting button on the canvas turns the markers off and on; it starts on, and is hidden while token simulation is running, since the canvas is showing something else at that point.

The same findings are in the Problems tab, beside the drawing problems, each with its error or warning icon and the id of the rule. Clicking a finding selects the element and opens the property that fixes it. See Check and problems.

On the command line

penstock check runs the same rules as one section of its report, beside the drawing, the engine compatibility rules and, on Pro, the flow analysis. penstock check --only rules runs the rules alone. A rule set to error makes the run fail; a warning is reported as a note.

penstock check --only rules .

In the IDE, Check in the context menu of the Penstock tool window runs penstock check on a file or folder and shows the report in the Run window. It runs only in a trusted project.

penstock lint still works in this release and says that it is now penstock check --only rules.

Custom rules

A custom rule comes from a bpmnlint-plugin-<name> package. Declare it in the project's package.json and run npm install: the command line reads plugins from the project's node_modules, with no installed bpmnlint needed.

The editor cannot load packages from node_modules. For a .bpmnlintrc that uses a plugin, build a bundle of the rules with bpmnlint-pack-config and name it with lint.clientBundlePath in penstock.yaml. Rebuild it whenever the rules change; the editor loads that bundle, not the .bpmnlintrc. Without it, the Rules group says The bpmnlint rules could not run and points at lint.clientBundlePath.

lint:
  configPath: .bpmnlintrc
  clientBundlePath: .bpmnlint/client.bundle.js

Only rules from a bpmnlint plugin need the bundle. A .bpmnlintrc that only uses built-in rules, and the compatibility rules, need nothing at all.
