Validation with bpmnlint

Penstock ships no rules of its own. A command-line run uses the bpmnlint binary installed in your project, against the .bpmnlintrc you write; the overlays in the diagram editor use the rules you compile into client.bundle.js. Validation stays off until you tell it where those three files are.

The three paths

Open Settings | Tools | Penstock and fill in the BPMN Lint Configuration group. Each field has a browse button.

bpmnlint binary: The executable Penstock runs. The field's own hint is e.g. node_modules/.bin/bpmnlint.
.bpmnlintrc config: Your rule configuration. The hint is project root or custom location. Its containing folder becomes the working directory of the lint process, which is how plugin resolution finds your rules.
client.bundle.js: The browser build of the same rule set, loaded into the diagram editor. The hint is e.g. .bpmnlint/client.bundle.js.

The three are all-or-none. If you set some and leave others empty, applying the settings fails with All three BPMN Lint paths must be configured. If a path is set but the file is not there, it fails with <path> not found. With all three empty, validation is off and nothing complains. The same rule is enforced when the paths are saved from the editor's own setup page.

Penstock starts the linter by invoking node, so Node.js has to be on the PATH the IDE was launched with.

A minimal .bpmnlintrc

Put this in the project root and point the config path at it:

{
  "extends": ["bpmnlint:recommended"],
  "rules": {
    "label-required": "error",
    "no-implicit-split": "warn"
  }
}

Custom rules

A custom rule comes from a bpmnlint-plugin-<name> package. bpmnlint resolves it with Node's own module resolution, starting from the folder that holds .bpmnlintrc, so the plugin has to be installed under that folder: declare it in package.json and run npm install, and keep the configuration next to the node_modules it depends on. Rebuild client.bundle.js whenever the rules change; the editor loads that bundle, not the .bpmnlintrc.

Trusted projects

A command-line run refuses to start in an untrusted project. This is deliberate — the run executes a binary from the project's own node_modules. Trust the project in the IDE first; until you do, nothing is started and the run reports BPMN Lint requires trusting this project first.

In the diagram editor

When all three paths are set, the editor loads the bpmnlint integration and reads client.bundle.js from disk, using its default export as the linter configuration. Overlays are toggled from the linting button on the canvas, which starts inactive. The button is hidden while token simulation is running, since the canvas is showing something else at that point. If the bundle cannot be read or evaluated, the editor reports Failed to load custom lint rules and the rest of the editor carries on working.

Running bpmnlint over a file

A full command-line run is started from the BPMN Project tool window, anchored on the left. Expand a diagram and you get a checkBpmnLint entry under it; double-click it, or select it and press Enter. The entry only appears once all three paths are configured, and the tool window only lists files once an engine profile has been chosen for the project.

Penstock then runs node <binary> --format pretty <file> with the working directory set to the folder containing your .bpmnlintrc, and attaches the process to the Run tool window under the title BPMN Lint – <name>, where the name is the diagram's file name without its extension. The window is brought to the front automatically. The stop button kills the process; a cancelled run prints BPMN lint execution cancelled. rather than pretending to have finished.

Output starts with Starting BPMN lint..., then bpmnlint's own pretty-printed report, then one closing line:

BPMN lint found critical issues. The report contains at least one error.
BPMN lint found non-critical issues. Warnings, no errors.
BPMN lint: no issues found. Clean report, process exited normally.
BPMN lint exited with errors (exit code N). A non-zero exit that produced no recognisable report — usually a broken configuration or a missing rule plugin. Read the lines above it.

Timeout and concurrent runs

A run is given 180 seconds. If the process is still alive after that and you have not stopped it yourself, Penstock terminates it, prints BPMN lint execution timed out. in the Run window, and raises a notification. Only one run per file is allowed at a time; starting a second one while the first is still going is refused rather than queued. Different files can be linted concurrently.

Error notifications

Failures are reported as error balloons titled Penstock.

Failed to find 'bpmnlint' npm package Shown with the suggestion to run npm install bpmnlint. Raised when the three paths are not all configured, when the configured .bpmnlintrc does not exist on disk, or when the binary path is blank.
BPMN Lint requires trusting this project first The project is not trusted. Nothing was executed.
BPMN Lint is already running for '<file>' A run for that same file has not finished. Wait for it, or stop it from the Run window.
BPMN lint execution timed out for file: '<file>' The 180-second limit was reached and the process was terminated.
Failed to run bpmnlint The process could not be started at all. The most common cause is node not being on the IDE's PATH; the IDE log has the underlying exception.

Where the paths are stored

The three paths are project settings and are written to bpmn-project.xml along with the engine profile and the rest of the project configuration. See Configuration.
