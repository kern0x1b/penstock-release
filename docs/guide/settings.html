Configuration

One file in the project root, penstock.yaml, says what the project is: which engine, which templates, which linter, where deploy sends it. It is hand-written, committed with the diagrams, overridden per folder, per machine, per profile and finally by the environment. Nothing about how your editor looks lives in it.

penstock.yaml

# yaml-language-server: $schema=https://kern0x1b.github.io/penstock-release/schema/penstock.schema.json

engine: camunda-7        # classic | camunda-7 | camunda-8
scriptType: groovy       # none | groovy | javascript

elementTemplates:
  - .camunda/element-templates

lint:
  binaryPath: node_modules/.bin/bpmnlint
  configPath: .bpmnlintrc
  clientBundlePath: .bpmnlint/client.bundle.js

layout:
  nodesep: 40
  ranksep: 80
  marginX: 40
  marginY: 40

deployment:
  url: http://localhost:8080/engine-rest
  name: Order handling
  source: penstock

profiles:
  test:
    deployment:
      url: https://bpm-test.example.com/engine-rest
      auth:
        type: basic
        username: ${BPM_USER:ci}
  prod:
    deployment:
      url: https://bpm.example.com/engine-rest
      duplicateFiltering: true
      auth:
        type: oauth
        clientId: penstock
        tokenUrl: https://auth.example.com/oauth/token

There is one deployment.url, not one per engine: engine already says whether that address is a Camunda 7 REST API or a Camunda 8 gateway. Everything is optional — what you leave out keeps its default.

Profiles

A profile is a named set of overrides, applied on top of everything above it. Choose one with profile: test in the file, or with the PENSTOCK_PROFILE environment variable, which wins — that is how a CI job deploys to staging without editing anything.

A profile beats the plain values in every file, including the local one. To override a profile on your own machine, put the key under profiles.<name> in penstock.local.yaml — which is exactly what the deployment dialog does when you change a target while a profile is active.

Four ways to override, in order

1. penstock.yamlThe project's answer, committed. Every folder from the root down to the diagram is merged, so the file nearest the diagram wins.
2. penstock.local.yamlThis machine's answer, in the same folders, read straight after the file beside it. Keep it out of version control; Penstock adds it to .gitignore when it writes one.
3. profiles.<name>The active profile, folded over the merged result.
4. PENSTOCK_*Environment variables have the last word: PENSTOCK_DEPLOYMENT_URL, PENSTOCK_ENGINE, PENSTOCK_LINT_CONFIGPATH — the key path in capitals, joined by underscores.

Any string may also reference the environment: ${VAR}, or ${VAR:fallback} when it may be missing. That is how a secret gets into the configuration without being written down in it.

Secrets

Passwords, bearer tokens, client secrets and API keys are never read from these files and never written to them. They go to the IDE password safe, and only when you ask for them to be remembered. A user name or a client id is not a secret and belongs in the file; what unlocks them does not.

What is not in the file

Nothing about the editor's appearance: theme, sketchy rendering, toolbar labels, whether the tool window shows its tree. Those are yours, not the project's, and they belong to your IDE — putting them in a file everyone shares means one person's dark theme arrives in everyone else's checkout.

Completion and validation

The plugin ships a JSON Schema and registers it for penstock.yaml, penstock.yml, penstock.json and their .local variants, so completion, validation and hover documentation work in the IDE with no setup and no network. The yaml-language-server line at the top is for everything else — VS Code, Neovim, a review in a browser — and is why the generated file starts with it.

A file Penstock cannot parse is reported in a notification naming the file and the error, and the previous answer stands until it parses. It is not ignored quietly.

Coming from the IDE settings

Older projects kept this in .idea/bpmn-project.xml. That file is legacy: it is read once, to offer the move. When a project has settings there and no penstock.yaml, a notification offers to write one, and the first-run Configure BPMN Engine screen writes the file rather than the XML. Penstock no longer has a page in Settings.

What belongs in version control

penstock.yamlCommit it. That is the point: everyone gets the same engine, the same lint setup, the same deployment targets, and a change to any of it is reviewed like any other change.
penstock.local.yamlDo not commit it. It is where your machine disagrees with the project.
.bpmnlayoutrcStill read if you have one. layout in penstock.yaml replaces it and wins.
CredentialsNothing to commit. They live in the IDE password safe, outside the project.
.bpmn and .bpmn20.xmlCommit them. They are the process definitions, and reviewing them alongside code is the point.
