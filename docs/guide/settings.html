Configuration

One file in the project root, penstock.yaml, says what the project is: which engine, which templates, which linter, where deploy sends it. It is hand-written, committed with the diagrams, overridden per folder, per machine, per profile and finally by the environment. Nothing about how your editor looks lives in it.

penstock.yaml

# yaml-language-server: $schema=https://kern0x1b.github.io/penstock-release/schema/penstock.schema.json

engine: camunda-7        # classic | camunda-7 | camunda-8
scriptType: groovy       # none | groovy | javascript

elementTemplates:
  - templates/connectors

lint:
  configPath: rules/.bpmnlintrc

tests:
  language: kotlin       # java | kotlin
  out: src/test/kotlin
  package: com.example.orders.process

deployment:
  url: http://localhost:8080/engine-rest
  name: Order handling
  source: penstock

profiles:
  test:
    deployment:
      url: https://bpm-test.example.com/engine-rest
      auth:
        type: basic
        username: ${BPM_USER:ci}
  prod:
    deployment:
      url: https://bpm.example.com/engine-rest
      auth:
        type: oauth
        clientId: penstock
        tokenUrl: https://auth.example.com/oauth/token

There is one deployment.url, not one per engine: engine already says whether that address is a Camunda 7 REST API or a Camunda 8 gateway. Everything is optional — what you leave out keeps its default.

elementTemplates lists files and folders relative to the project root; a .camunda/element-templates folder next to a diagram or above it is read without being listed. lint is only needed when the rules are not in a .bpmnlintrc in the project root, or come from a bpmnlint plugin; see Element templates and Validation. There are no layout settings: auto layout uses its own spacing, and .bpmnlayoutrc is not read.

tests is only needed when the defaults are wrong. Without it, penstock tests puts each diagram's tests in its own module - the nearest folder with a Gradle or Maven build - in Kotlin if that module has Kotlin sources and Java otherwise, in the package of its Spring Boot application, or the one all its sources share, followed by .process. out is relative to the project root.

Profiles

A profile is a named set of overrides, applied on top of everything above it. Choose one with profile: test in the file, or with the PENSTOCK_PROFILE environment variable, which wins — that is how a CI job deploys to staging without editing anything.

A profile beats the plain values in every file, including the local one. To override a profile on your own machine, put the key under profiles.<name> in penstock.local.yaml — which is exactly what the Connection dialog does when you enter an engine address for a profile. See Deployment.

Four ways to override, in order

1. penstock.yamlThe project's answer, committed. Every folder from the root down to the diagram is merged, so the file nearest the diagram wins.
2. penstock.local.yamlThis machine's answer, in the same folders, read straight after the file beside it. Keep it out of version control; Penstock adds it to .gitignore when it writes one.
3. profiles.<name>The active profile, folded over the merged result.
4. PENSTOCK_*Environment variables have the last word: PENSTOCK_DEPLOYMENT_URL, PENSTOCK_ENGINE, PENSTOCK_LINT_CONFIGPATH — the key path in capitals, joined by underscores.

Any string may also reference the environment: ${VAR}, or ${VAR:fallback} when it may be missing. That is how a secret gets into the configuration without being written down in it.

Rules the editor applies for you

Camunda's own guidance asks for readable technical ids, and every team writes the convention down somewhere and then forgets it. Put it in the file instead - the editor applies it on Penstock Pro:

conventions:
  ids:
    fromName: true
    pattern: "{Type}_{Name}"      # "Check stock" on a service task -> ServiceTask_CheckStock
  defaults:
    bpmn:ServiceTask:
      camunda:asyncBefore: true

ids rewrites the id when the label changes, keeping it unique by adding a number rather than colliding. defaults sets attributes on an element as it is created — and morphing counts as creating, since a task that becomes a service task is how most service tasks are made. Both happen inside the same modelling command, so one undo takes them back together with the change that caused them.

Commands around a stage

hooks:
  preDeploy: npm run verify-workers
  postDeploy: ./notify-release.sh
  postLayout: git add -A

These run when the command line reaches that stage, in the project root, with PENSTOCK_FILES, PENSTOCK_ROOT, PENSTOCK_STAGE and the active profile in the environment. preDeploy and postDeploy also run around a deployment from the IDE, and there only in a trusted project. A pre hook that exits non-zero stops the stage — which is how a project says "not without this check".

Secrets

Passwords, bearer tokens and client secrets are never read from these files and never written to them. In the IDE they go to the password safe, separately for each profile, when you enter them in the Connection dialog. On the command line they come from PENSTOCK_PASSWORD, PENSTOCK_CLIENT_SECRET and PENSTOCK_TOKEN. A user name or a client id is not a secret and belongs in the file; what unlocks them does not.

What is not in the file

Nothing about the editor's appearance. The diagram always takes the IDE's theme. The rest - which toolbar actions are pinned, Sketchy Drawing, whether the tool window shows a tree or a flat list, the picture format its Export… item last used - is yours, not the project's, and lives in ~/.penstock/preferences.json, or under PENSTOCK_HOME when that is set. It is the same in every IDE on the machine and survives a restart. Putting it in a file everyone shares would mean one person's toolbar arriving in everyone else's checkout.

Completion and validation

The plugin ships a JSON Schema and registers it for penstock.yaml, penstock.yml, penstock.json and their .local variants, so completion, validation and hover documentation work in the IDE with no setup and no network. The yaml-language-server line at the top is for everything else — VS Code, Neovim, a review in a browser — and is why the generated file starts with it.

A file Penstock cannot parse is reported in a notification naming the file and the error, and the previous answer stands until it parses. It is not ignored quietly.

Coming from the IDE settings

Older projects kept this in .idea/bpmn-project.xml. That file is legacy. When a project has settings there and no penstock.yaml, a notification offers to write one, and the engine question above an empty new diagram writes the file rather than the XML. Penstock has no page in Settings.

What belongs in version control

penstock.yamlCommit it. That is the point: everyone gets the same engine, the same lint setup, the same deployment targets, and a change to any of it is reviewed like any other change.
penstock.local.yamlDo not commit it. It is where your machine disagrees with the project.
.bpmnlintrc, .camunda/element-templatesCommit them. They are the project's rules and templates, read by the editor and the command line alike.
.bpmnlayoutrcNo longer read. Delete it.
CredentialsNothing to commit. They live in the IDE password safe, outside the project.
.bpmn and .bpmn20.xmlCommit them. They are the process definitions, and reviewing them alongside code is the point.
