Command line

The editor is one way to use this project; a terminal is the other. The same penstock.yaml, the same profiles, the same checks — without an IDE, which is what makes them usable in a pipeline.

Running it

npx @penstock/cli check .
npx @penstock/cli lint .
npx @penstock/cli deploy . --profile prod

Or pin a version for everyone, the way gradlew does. penstock init writes the same layout Gradle uses:

penstockw                                    run this instead of penstock
penstockw.cmd                                the same, on Windows
penstock/wrapper/penstock-wrapper.properties the version, and where to get it

Commit all three, and a laptop and a CI runner cannot disagree about which version they are running. The CLI itself is not committed: the first run downloads the pinned version into ~/.penstock/wrapper/dists, and every run after that starts from there, offline.

./penstockw check .
./penstockw update          # the latest version
./penstockw update 2.5.0    # a version of your choosing

update pins the version, downloads it, and replaces the wrapper scripts with the ones that version ships, as gradle wrapper does. Editing the version in the properties file by hand works too — the next run notices it is not downloaded yet and fetches it. A company registry or a tarball goes in distribution= in the same file.

Paths default to the working directory, and the configuration is read from there upward, so it does not matter which folder you run it in — the same rule Maven follows with a pom.

Commands

initWrite a penstock.yaml with the engine guessed from the diagrams already in the repository, add the local file to .gitignore, install the wrapper. --ci github or --ci gitlab writes the pipeline as well.
configPrint what applies and which layers it came from. --json for a machine.
profilesList the profiles on offer, marking the active one.
doctorAnswer "why does it not work": configuration found, linter present, templates resolvable, engine reachable.
checkThe drawing defects the editor's own panel reports — overlaps, detached connections, elements outside their pool. Exits non-zero when it finds any.
lintbpmnlint with the project's own rules, grouped by the folder each diagram belongs to.
layoutLay the diagrams out with the project's spacing. --write saves; without it, it says what would change.
fmtRewrite the XML the way the editor saves it, so a renamed task is a one-line diff. --write saves.
diffWhat changed between two versions of a process: added, removed and changed elements by name, and "only the drawing moved" when that is all.
exportRender the diagrams as SVG, with nothing to install. PNG needs puppeteer in the project.
againstWhat this working tree changed since a commit, branch or tag. --images renders before and after with the changes coloured in.
reportOne markdown comment for a pull request: check, diff against the base, and pictures with the changes outlined.
deploySend the diagrams to the engine the configuration names, grouped by the target each folder asks for. --dry-run says where without sending; --wait confirms the definitions are live.

In a pipeline

penstock init --ci github writes this, and --ci gitlab writes its equivalent:

name: Diagrams

on: [push, pull_request]

jobs:
  penstock:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx @penstock/cli check . --format sarif > penstock.sarif
      - uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: penstock.sarif

check speaks three machine formats besides its own: --format sarif produces SARIF 2.1.0, which GitHub code scanning reads directly and turns into annotations on the pull request; --format github produces the annotation lines for a workflow that does not use code scanning; --format json is for everything else.

Only what is new

A first run on a repository that has been drawing diagrams for years is red, and a red build nobody can fix gets switched off. Record what the project already lives with, and check against it from then on:

penstock check . --update-baseline   # writes penstock-baseline.json, commit it
penstock check . --baseline          # fails only on what is new

It also says what has been fixed since the baseline was taken, so the file can be refreshed when the backlog shrinks.

Before the commit

penstock init --hooks installs a pre-commit hook that formats and checks the diagrams a commit is carrying, and nothing else. It lives in .git/hooks, so it is yours rather than the repository's, and deleting the file removes it.

Pictures

penstock export . --out docs/img

SVG, drawn by penstock itself from the diagram's own coordinates — no browser, nothing to install, the same picture on a laptop and in CI. --format png paints that SVG into pixels, and that one step does need a browser: install puppeteer in the project for it. Everything else, including the pictures in pull request reviews, is SVG.

Editing from the command line

penstock edit changes a diagram the way the editor would, not by rewriting XML: a new element is placed and connected by the editor's own modelling, gets an id from the project's conventions, and carries only properties the project's engine knows.

penstock show orders.bpmn
penstock edit orders.bpmn add service-task --after Task_check --name "Reserve stock" --set jobType=reserve-stock
penstock edit orders.bpmn connect Gateway_stock Task_notify --condition "=not(inStock)"
penstock edit orders.bpmn set Task_notify --set assignee=support --input customer==order.customer
penstock edit orders.bpmn remove Task_legacy

The same changes can be given as JSON with --ops, which is the contract: penstock edit orders.bpmn --schema prints it for the project's engine, and an unknown operation, field or property is refused rather than ignored. Several operations apply together or not at all. After an edit the diagram is read back and checked; one that would break the drawing — shapes on top of each other, a flow through a shape, a flow torn from its element — is not written, and a crossing or a flow running along a shape is reported without stopping it. --dry-run shows the result without writing.

For an AI agent

penstock mcp serves the project's diagrams over the Model Context Protocol, with the same contract: list_diagrams, show_diagram, check_diagram and edit_diagram, limited to files inside the project. penstock mcp --config prints the entry for a client's configuration.

A bot in the repository

The bot is penstock bot running in your own CI. There is no service behind it and nothing to register: it answers with the token of the pipeline it runs in, and penstock init --ci <github|gitea|forgejo|gitlab|bitbucket|azure> writes the pipeline for it.

On a pull or merge request that touches a diagram it leaves one comment and edits that same comment on every push: what broke against the baseline, what changed in the process — by element, from the semantic diff, not from the XML — and a picture with what arrived in green and what differs in amber. In the conversation it answers:

/penstock                    the full review
/penstock check              only the problems
/penstock diff v1.4.0        what changed since a commit, branch or tag, outlined
/penstock image orders.bpmn  a picture of the diagram as it is now
/penstock help

The picture is drawn by penstock itself, without a browser, and goes wherever the platform lets a pipeline put it. Nothing is ever committed to the repository.

PlatformComments answeredThe pictureWhat to add
GitHubyeskept with the run, opens in the browser from the link in the commentnothing
Gitea, Forgejoyesattached to the pull request, shown inlinenothing
GitLabyes, through a webhook on the pipeline triggeruploaded to the project, shown inlinePENSTOCK_TOKEN, a project access token
Azure DevOpsno, the review onlyattached to the pull request, shown inlinelet the build service contribute to pull requests
Bitbucketno, the review onlya pipeline artifact, linked from the commentPENSTOCK_TOKEN, a repository access token

The bot reads the diagrams and penstock.yaml, and never runs the hooks a pull request's configuration might declare.

init --ci github also writes a publishing workflow: on merge, penstock deploy . --wait with the prod profile and the secrets from the environment. --wait matters — it asks the engine for the definitions it just accepted until the engine answers, because "deployed" and "running" are not the same claim.

The action

- uses: kern0x1b/penstock-release@main
  with:
    command: check
    baseline: 'true'
    sarif: penstock.sarif

The action runs the project's penstockw when there is one, so CI runs exactly the version the project pins, and keeps the download cached between runs.

Deploying from CI

PENSTOCK_PROFILE=prod \
PENSTOCK_PASSWORD=$CAMUNDA_PASSWORD \
npx @penstock/cli deploy .

The profile chooses the environment, and the secret arrives through the environment rather than through the repository. PENSTOCK_TOKEN is used as a bearer token when the engine wants one, and any PENSTOCK_* variable matching a configuration key overrides it for that run — PENSTOCK_DEPLOYMENT_URL to send one build somewhere else, for instance.

Run penstock deploy --dry-run first in a new pipeline: it prints the target and the file list, and sends nothing.
