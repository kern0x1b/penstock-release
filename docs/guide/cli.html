Command line

The editor is one way to use this project; a terminal is the other. The same penstock.yaml, the same profiles, the same checks - without an IDE, which is what makes them usable in a pipeline.

Running it

npx @penstock/cli check .
npx @penstock/cli doctor
npx @penstock/cli deploy . --profile prod

Or pin a version for everyone, the way gradlew does. penstock init writes the same layout Gradle uses:

penstockw                                    run this instead of penstock
penstockw.cmd                                the same, on Windows
penstock/wrapper/penstock-wrapper.properties the version, and where to get it

Commit all three, and a laptop and a CI runner cannot disagree about which version they are running. The CLI itself is not committed: the first run downloads the pinned version into ~/.penstock/wrapper/dists, and every run after that starts from there, offline.

./penstockw check .
./penstockw update          # the latest version
./penstockw update 26.10.0  # a version of your choosing

update pins the version, downloads it, and replaces the wrapper scripts with the ones that version ships, as gradle wrapper does. Editing the version in the properties file by hand works too - the next run notices it is not downloaded yet and fetches it. A company registry or a tarball goes in distribution= in the same file.

Paths default to the working directory, and the configuration is read from there upward, so it does not matter which folder you run it in - the same rule Maven follows with a pom.

Commands

A command marked Pro is a paid one, and one rule decides what it needs: Pro on your machine, Team in a pipeline, which is any run with CI set. See Plans and licence.

initWrite a penstock.yaml for this project and add the local file to .gitignore, and install the wrapper. --engine camunda-8|camunda-7|operaton|cib-seven|classic says what the project runs on; in a terminal on an empty project init asks with a numbered choice instead, and anywhere else it guesses from the diagrams. --example camunda-8|camunda-7 writes a small project that runs into an empty folder: an order process with a service task, a user task with a Camunda Form, a decision, a message and an error boundary, workers for the engine, test cases in the Camunda format, a penstock.yaml and a README with the commands to run it against a local engine. --ci <github|gitea|forgejo|gitlab|bitbucket|azure> writes a pipeline as well, for the licence on the machine; --hooks installs a pre-commit hook.
doctorAnswer "why does it not work": which configuration files apply, the engine, the profiles on offer with the active one marked, the rules and templates the configuration names, whether the engine is reachable, and whether a deployment would be sent credentials it does not have. --format json prints the configuration that applies.
checkEverything wrong with the diagrams in one run, in sections. drawing: the defects the editor's own check reports - overlaps, detached connections, elements outside their pool. rules: bpmnlint, with the project's .bpmnlintrc or bpmnlint:recommended, the engine compatibility rules, and plugins from the project's node_modules, plus the form checks on .form files, which are free. flow, on Pro: whether each process can actually run - deadlocks, branches that run twice, steps that can never run, loops with no way out, each with the path that leads there - and, on .dmn files, overlapping rules and inputs no rule matches. --only drawing,rules,flow runs part of it. Exits non-zero when it finds an error.
migrate [analyze|convert|report]Camunda 7, Operaton or CIB seven to Camunda 8. analyze says what does not carry over, convert writes the Camunda 8 files and the job worker skeletons (Pro), and report writes the report to hand on, which is free. --format text|json|sarif|github, --fail-on warning, --baseline, --target 8.5 to 8.9, --dry-run and --out <dir>. The exit code follows check. See Camunda 7 to Camunda 8.
codePro. Compare the diagrams with the code: a service task, listener or external task whose job type, topic, class or Spring bean has nothing in the project to run it, a call activity that calls a process no diagram defines, and a worker no diagram uses - each with the file and line. Workers are read from Java, Kotlin, Groovy, Scala, Python, JavaScript, TypeScript, Go and C#; connectors and job types set by an expression are understood. The repositories named by linked are read as part of the project.
scenarios listPro. Every distinct way through each process, with the decision taken at each gateway and its condition. --format md writes it as a checklist for a test plan.
scenarios runPro. Run the Camunda test-case files against their engine, step by step, with mocks. --teamcity for service messages, as the IDE reads them; --junit-xml <file> for a report; --timeout for how long one step may take.
scenarios generatePro. Write the test-case files from the ways through each process, one scenario per way, keeping the ones already in the file. A process that starts on a message, a timer or a signal is planned from that start event.
junitPro. A JUnit test for every way through each process, with the variables that take it there. Camunda Process Test for Camunda 8, camunda-bpm-assert with an in-memory engine for Camunda 7, Operaton and CIB seven, each with its own Java packages. --out <dir> and --package <name> choose otherwise.
docsPro. A page for every process - its picture, steps with who and what runs them, decisions and their conditions, events, the data each step sets and reads, and whether it runs to its end - a page for every .dmn file, with each decision's rules, hit policy and what it needs, and the table check; and a page for every Camunda Form with the variable each field writes. HTML by default, --format md for a wiki, into --out. Reads DMN 1.1 and 1.2 files by moving them to 1.3 first.
layoutPro. Lay the diagrams out. --write saves; without it, it says what would change.
fmtRewrite the XML the way the editor saves it, so a renamed task is a one-line diff. --write saves.
diffWhat changed in a process: added, removed and changed elements by name, and "only the drawing moved" when that is all. Give it two files to compare them, or a commit, branch or tag - HEAD~1 by default - and optionally paths, for what the working tree changed since then. --images, Pro, renders before and after with the changes coloured in.
exportRender the diagrams as SVG, with nothing to install. PNG needs puppeteer in the project.
share <file>One HTML file to send: a read-only viewer with zoom, pan and the documentation of each element, which opens offline and loads nothing. -o out.html. Free. See Sharing and importing.
import <file>Turn a draw.io, Visio, Signavio or Bizagi diagram into BPMN 2.0, and list what could not be mapped. -o out.bpmn, --force. Free. See Sharing and importing.
connectors [resolve <id>]List Camunda's connector templates, or print one. Downloaded from GitHub at most once a day, cached where the IDE reads it too; --refresh checks now.
reportPro. One markdown comment for a pull request: check, diff against the base, and pictures with the changes outlined.
botAnswer in a pull or merge request, from the CI run it is in. Team. init --ci sets it up.
deploySend the diagrams, decisions (.dmn) and forms (.form) to the engine the configuration names, grouped by the target each folder asks for. --dry-run says where without sending; --wait confirms the definitions are live.
show <file>List a diagram's elements, flows and properties. --format json for tools.
edit <file>Pro. Add, connect, set or remove, the way the editor would. --ops for JSON, --schema for the contract. See below.
license [status|key]Which licence this machine has, or its key for a pipeline. license buy, license login and license logout buy Penstock, sign in and release this machine. See Plans and licence.
mcpServe the project's diagrams to an AI agent over the Model Context Protocol. See below.
update [version]Move the project's wrapper to a version, the latest by default.

The scenario commands are named after what they do. The old names still work and are left out of the help: paths is scenarios list, test-cases is scenarios run, test-cases --generate is scenarios generate, and tests is junit. lint and analyze are check --only rules and check --only flow, against is diff <ref>, config and profiles are doctor, upgrade, login and logout are license buy, license login and license logout, wrapper is update, and the flags --json and --image are --format json and --images. The Run Penstock menu in the IDE uses the new names.

In a pipeline

penstock init --ci github writes a pipeline for the licence on the machine, and the other platforms get their equivalent. Without Team it runs the free check - the drawing and the rules - so its first run does not fail on a feature nobody has bought:

name: Diagrams

on: [push, pull_request]

jobs:
  penstock:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - uses: kern0x1b/penstock-release@main
        with:
          command: check

With Team on the machine, the same step passes PENSTOCK_LICENSE from the repository's secrets, writes SARIF against the baseline and uploads it to code scanning, and the review bot is set up beside it. The pipeline it writes runs when a .bpmn, .bpmn20.xml, .bpmn.xml, .dmn or .form file changes, not only on a .bpmn.

check speaks three machine formats besides its own: --format sarif produces SARIF 2.1.0, which GitHub code scanning reads directly and turns into annotations on the pull request; --format github produces the annotation lines for a workflow that does not use code scanning; --format json is for everything else. SARIF and annotations are Pro, and Team in a pipeline, and cover every section of the check. Every finding carries the id of its check and the link to its page.

Only what is new

A first run on a repository that has been drawing diagrams for years is red, and a red build nobody can fix gets switched off. Record what the project already lives with, and check against it from then on:

penstock check . --update-baseline   # writes penstock-baseline.json, commit it
penstock check . --baseline          # fails only on what is new

It also says what has been fixed since the baseline was taken, so the file can be refreshed when the backlog shrinks. A baseline covers every section of the check; one taken before the check had sections needs refreshing with --update-baseline. Baselines are Pro, and Team in a pipeline.

Before the commit

penstock init --hooks installs a pre-commit hook that formats and checks the diagrams a commit is carrying, and nothing else. It lives in .git/hooks, so it is yours rather than the repository's, and deleting the file removes it.

Pictures

penstock export . --out docs/img

SVG, drawn by penstock itself from the diagram's own coordinates - no browser, nothing to install, the same picture on a laptop and in CI. --format png paints that SVG into pixels, and that one step does need a browser: install puppeteer in the project for it. Everything else, including the pictures in pull request reviews, is SVG.

Editing from the command line

penstock edit changes a diagram the way the editor would, not by rewriting XML: a new element is placed and connected by the editor's own modelling, gets an id from the project's conventions, and carries only properties the project's engine knows.

penstock show orders.bpmn
penstock edit orders.bpmn add service-task --after Task_check --name "Reserve stock" --set jobType=reserve-stock
penstock edit orders.bpmn connect Gateway_stock Task_notify --condition "=not(inStock)"
penstock edit orders.bpmn set Task_notify --set assignee=support --input customer==order.customer
penstock edit orders.bpmn remove Task_legacy

The same changes can be given as JSON with --ops, which is the contract: penstock edit orders.bpmn --schema prints it for the project's engine, and an unknown operation, field or property is refused rather than ignored. Several operations apply together or not at all. After an edit the diagram is read back and checked; one that would break the drawing - shapes on top of each other, a flow through a shape, a flow torn from its element - is not written, and a crossing or a flow running along a shape is reported without stopping it. --dry-run shows the result without writing.

For an AI agent

penstock mcp serves the project's diagrams over the Model Context Protocol, limited to files inside the project. penstock mcp --config prints the entry for a client's configuration. The server is not gated as a whole: each tool is priced like the command it stands for, and nothing else.

list_diagramsFree. The diagrams in the project.
show_diagramFree. One diagram, read and explained.
check_diagramFree. What is wrong with one diagram, with the id of each check.
analyze_flowPro. Flow analysis, as check --only flow does it.
list_scenariosPro. As scenarios list.
check_code_linksPro. As code.
edit_diagramPro. As edit.

A tool called without the licence says in its result what it gives and how to buy or sign in, rather than failing quietly, and it still appears in tools/list with a note on what it needs - so an agent can tell the difference between "this is not allowed" and "this does not exist". An agent that edits a diagram can check straight away that it still runs to its end.

A bot in the repository

The bot is penstock bot running in your own CI, so it needs Team. There is no service behind it and nothing to register: it answers with the token of the pipeline it runs in, and penstock init --ci <github|gitea|forgejo|gitlab|bitbucket|azure> writes the pipeline for it.

On a pull or merge request that touches a diagram it leaves one comment and edits that same comment on every push: what broke against the baseline, what changed in the process - by element, from the semantic diff, not from the XML - and a picture with what arrived in green and what differs in amber. In the conversation it answers:

/penstock                    the full review
/penstock check              only the problems
/penstock diff v1.4.0        what changed since a commit, branch or tag, outlined
/penstock image orders.bpmn  a picture of the diagram as it is now
/penstock help

The picture is drawn by penstock itself, without a browser, and goes wherever the platform lets a pipeline put it. Nothing is ever committed to the repository.

PlatformComments answeredThe pictureWhat to add
GitHubyeskept with the run, opens in the browser from the link in the commentnothing

The bot reads the diagrams and penstock.yaml, and never runs the hooks a pull request's configuration might declare.

The action

- uses: kern0x1b/penstock-release@main
  with:
    command: check
    baseline: 'true'
    sarif: penstock.sarif

The action runs the project's penstockw when there is one, so CI runs exactly the version the project pins, and keeps the download cached between runs.

Deploying from CI

PENSTOCK_PROFILE=prod \
PENSTOCK_PASSWORD=$CAMUNDA_PASSWORD \
npx @penstock/cli deploy .

The profile chooses the environment, and the secret arrives through the environment rather than through the repository. With auth.type: oauth the client secret comes from PENSTOCK_CLIENT_SECRET. PENSTOCK_TOKEN is used as a bearer token when the engine wants one, and any PENSTOCK_* variable matching a configuration key overrides it for that run - PENSTOCK_DEPLOYMENT_URL to send one build somewhere else, for instance.

Run penstock deploy --dry-run first in a new pipeline: it prints the target and the file list, and sends nothing.
