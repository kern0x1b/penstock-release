Engine profiles

A project targets one of five engines: Classic BPMN 2.0, Camunda 7, Camunda 8, Operaton or CIB seven. The choice decides which modeler is built, which groups the properties panel shows, and which namespace the editor is able to write into the diagram.

Choosing a profile

The engine is engine in penstock.yaml: one of classic, camunda-7, camunda-8, operaton or cib-seven. The file nearest the diagram wins, so a folder can have an engine of its own; see Configuration. When no file sets it, the diagram decides: the execution platform the Camunda Modeler records in it, or the zeebe:, camunda: or operaton: attributes it already carries. penstock init --engine says it outright, and penstock init recognises all five in the diagrams already in the repository.

A diagram opens straight away either way. Only an empty new diagram, which names no engine, asks: one line above the canvas, Which engine runs this diagram?, with a button for each of the five. The answer goes into penstock.yaml. Changing the engine takes effect when the diagram editor is reloaded, because the modeler is constructed from it.

A project with Camunda 7 and Camunda 8 diagrams needs nothing special: give each folder its own penstock.yaml. Code links keep the two apart, so a Camunda 8 job type finds its job worker and never an external task subscription of the same name, and a Camunda 7 topic finds the subscription and never a job worker.

What each profile builds

Classic BPMN 2.0

Classic uses the plain bpmn-js modeler with the standard properties panel and the standard BPMN properties provider, and it registers no engine namespace at all. Because no extension is registered, this profile cannot write camunda: or zeebe: attributes: there is nothing in the model that knows those types exist. The panel shows the groups the BPMN provider defines - General, Documentation, and the element-specific ones such as Message, Signal, Error, Escalation, Link, Timer, Compensation, Multi-instance and Ad-hoc completion - plus the colour picker in the context pad and the grid with snapping, which the Camunda profiles already had.

It is called Classic BPMN everywhere in the interface. The penstock.yaml value stays engine: classic.

Camunda 7

Camunda 7 uses the Camunda Platform modeler from camunda-bpmn-js. That modeler registers the camunda moddle extension and adds the Camunda Platform properties provider and the element-templates properties provider on top of the standard BPMN groups, so the panel gains the execution groups - among them Script, Condition, Execution listeners, Task listeners, Inputs and Outputs.

Penstock loads two more modules into this profile. One is the element-template create and append module, which the Camunda Platform modeler does not carry on its own, fed by the same template files as Camunda 8. The other is a properties provider of Penstock's own: script, condition, listener and input/output entries that hold an inline script are replaced with a CodeMirror field with Groovy or JavaScript highlighting, and that field can be opened as a real file in the IDE; while the file is open the field in the panel is read-only and the two stay in step. When scriptType is set in penstock.yaml, it is used as the scriptFormat of a script that does not have one yet, and as the language of a condition expression that does not have one yet. It applies to this family only.

Camunda 8

Camunda 8 uses the Camunda Cloud modeler from camunda-bpmn-js. It registers the zeebe moddle extension and adds, among others, the Zeebe properties provider, the cloud element-templates provider and the example data provider, and it points the panel's FEEL popup at the Camunda documentation for FEEL and for templating syntax. This modeler already carries both create and append modules, so a new element can be started from an element template or from the full element list.

The connector template browser, Templates…, appears only for this profile. See Element templates.

Operaton

Operaton and CIB seven are the community continuations of Camunda 7, and Penstock treats them as engines in their own right rather than as Camunda 7 with another address.

Operaton uses the Camunda Platform modeler, so the panel is the Camunda 7 one. It writes its own namespace, operaton: bound to http://operaton.org/schema/1.0/bpmn, and reads a camunda: attribute as the operaton: one, so a Camunda 7 diagram opens and edits with no migration step. In a project on Operaton, Penstock offers to convert the camunda: namespace of a Camunda 7 diagram it finds and says what it changed. The properties panel in the decision editor shows the id and the name of a decision and nothing else.

CIB seven

CIB seven uses the Camunda Platform modeler and writes the camunda namespace, which is what it reads. The difference is in what Penstock writes for you: the Java packages of a generated JUnit test and the engine's own test configuration file. The decision editor's properties panel gives a decision its version tag and its history time to live, as Camunda 7 does.

What reaches the XML

Classic BPMN 2.0BPMN 2.0 only. No engine namespace is registered, so none can be written.
Camunda 7camunda, bound to http://camunda.org/schema/1.0/bpmn.
Camunda 8zeebe, bound to http://camunda.org/schema/zeebe/1.0.
Operatonoperaton, bound to http://operaton.org/schema/1.0/bpmn.
CIB sevencamunda, bound to http://camunda.org/schema/1.0/bpmn.

So a service task configured under Camunda 7 carries attributes and extension elements such as camunda:asyncBefore or camunda:executionListener, and the same task configured under Camunda 8 carries zeebe:taskDefinition or zeebe:ioMapping. An element created from an element template records the template it came from in the same namespace - camunda:modelerTemplate under Camunda 7, zeebe:modelerTemplate under Camunda 8.

Nothing rewrites a diagram on open. If you switch a project from Camunda 7 to Classic, the camunda: content already in the file is left alone; the editor no longer has a panel for it, and the model no longer recognises those types.

Where a deployment goes

Camunda 7, Operaton and CIB seven all answer on the same engine-rest path, so one deployment.url covers the family. Camunda 8 has its own REST address. The generated tests differ: each engine's own Java packages and its own test configuration file, so org.camunda for Camunda 7, org.operaton for Operaton and org.cibseven for CIB seven. See Deployment.

Input and output in Classic

Classic writes data inputs and outputs the way BPMN defines them, not the way an engine extends it. Select a task, a sub-process or the process itself and the panel offers an Inputs and an Outputs group; adding an entry writes a bpmn:ioSpecification with a bpmn:dataInput or bpmn:dataOutput inside it, and a reference from the input or output set:

<bpmn:serviceTask id="Task_check" name="Check stock">
  <bpmn:ioSpecification>
    <bpmn:dataInput id="DataInput_1" name="quantity" />
    <bpmn:inputSet id="InputSet_1" name="Inputs">
      <bpmn:dataInputRefs>DataInput_1</bpmn:dataInputRefs>
    </bpmn:inputSet>
    <bpmn:outputSet id="OutputSet_1" name="Outputs" />
  </bpmn:ioSpecification>
</bpmn:serviceTask>

The ID is the one written into the file; the name is what the diagram calls it. Removing the last input and the last output removes the specification with them, so a file never carries an empty one. The groups are registered only in the Classic profile: the other profiles keep their own input and output editors, which write camunda:inputOutput and zeebe:ioMapping, because that is what those engines read.

Known limitations

The engine is set per folder, not per file: a penstock.yaml that sets engine applies to every diagram under its folder. The diagram's own attributes are read only where no file sets it.
