Run tests

Run tests lets you run the diagram's test cases on a local engine and see every step: the path taken and the variables that came in, went out and changed.

Pro Team in a pipeline. A local Camunda 7, Camunda 8, Operaton or CIB seven engine.

What it is

Run tests needs no build setup. The test cases are JSON files that Penstock runs against an engine for you.

A run starts the process on a real engine, answers its tasks with mocks that you choose, and shows the path it took on the diagram. For each step you see what came in, what went out, and what changed. A test case is a saved run that can be repeated. Test cases are ordinary JSON files, so they live in Git and run in a pipeline.

A step that a mock answered carries a Mocked badge. A green run over mocks is not proof that your code works. The badge says so.

Before you begin

  1. Start an engine on your machine. The example project tells you how.
  2. Make sure the profile in force has a deployment.url. See Profiles.
  3. Deploy nothing by hand. The run deploys its own test build and removes it afterwards.
Safety

A run deploys a test build, starts instances and answers jobs. So Penstock runs only on an engine that is marked for tests: deployment.forTests: true in penstock.yaml, or an engine on this machine that you confirm once. It asks once per profile in the editor, and once per run in a terminal. It never asks in a pipeline: there you need the forTests mark. Every other engine is refused, by the editor and by the host. See Security and privacy.

Run a test case in the editor

  1. Open the diagram and press Run tests on the toolbar. A panel opens under the canvas. It lists the diagram's test cases with their last result.
  2. Press Run all, or click one test case.
  3. Watch the diagram. Completed steps turn green, the step that failed turns red, the step it is waiting at turns blue.
  4. Read the table: Step, State, In, Out, Changed. Click a row to select the element. Select an element to see its row.

Where the values come from

On Camunda 7 the engine keeps a full history, so the table is exact. On Camunda 8 the engine keeps no variable history. The path is exact. What a mock received and sent is known. Decisions are read from the engine. Everything else is the difference between two readings, attributed to the stretch between them, not to one step. The panel says which.

Run with input

Use it to try a process by hand.

  1. In the Run tests panel press Run with input…. A dialog called Run with input opens.
  2. Type the Start variables as JSON. They are filled in from the variables the diagram reads.
  3. Under Steps choose what happens at each service task: Ask me, Complete (with variables), Throw error, Fail, then complete, or Real worker. For a timer choose Fire now or Wait for it.
  4. Press Run.
  5. The run stops at every step left to ask. The panel says Waiting at Charge card for the job charge-card, shows what was received, and asks what to send. Type the variables, or an error code, and answer. For a user task, complete it. For a message, press Correlate.

Save a run as a test case

  1. When an ad-hoc run has finished, press Save as test case….
  2. Give it a name. Untick any variable that is incidental: the test case checks the path taken and the variables that are ticked.
  3. Press Save. The test case is written to the file for this diagram.

Generate test cases

Press Generate in the Run tests panel, or run penstock test-cases --generate .. Penstock writes one test case for every way through the process, with example variables and a completing mock for every task. Test cases already in the file are kept.

$ penstock test-cases --generate .
wrote src/test/resources/test-cases/order-process.json  2 new test case(s)

Open a run that already exists

Press Open run… and give the key or id of a process instance. Penstock reads its path and steps from the engine of the profile and shows them on the diagram. It only reads, so it works on any engine the profile can read, and it is free.

The test case file

Test cases are Camunda Process Test JSON test cases, the same format that Camunda's Web Modeler reads. The file is src/test/resources/test-cases/<diagram>.json in a Maven or Gradle module, or test-cases/<diagram>.json next to the diagram. Every tool uses the same place.

Penstock's own additions go in an x-penstock block on the test case, which Camunda's tools ignore:

"x-penstock": {
  "engines": ["camunda-8", "camunda-7"],
  "behaviours": {
    "ReserveStock": { "fail": 2, "then": "complete", "variables": { "reserved": 3 } },
    "WaitForPayment": { "then": "fire" }
  }
}

A test case that needs a behaviour is tagged Penstock only, because Camunda Process Test would run it differently.

Run many test cases at once

The panel runs the test cases of the diagram you have open. Your tool can also run the test-case files of a whole project, one after another, and report pass or fail for each.

Run test-case files in your tool

JetBrains

Open a test-case file and press the green triangle in the gutter next to a test case. Or right-click the file or a folder and run it. The IDE's Run window shows a test tree, pass or fail, and the log. See Tests in the IDE.

Command line

penstock test-cases .
penstock test-cases src/test/resources/test-cases/orders.json
penstock test-cases . --junit-xml build/test-cases.xml --timeout 60
penstock test-cases . --teamcity

Test cases run one after another. The command exits with 1 if any fails. In a pipeline the engine needs deployment.forTests: true. See Every command.

What you see

  • The path of the run on the diagram, and a table of every step with what came in, went out and changed.
  • A Mocked badge on each step that a mock answered.
  • For a whole project: pass or fail for each test case, and a total such as 2 passed, 0 failed, 0 skipped in 1 file.

Common problems

"is not marked deployment.forTests: run in a terminal to confirm it once, or mark the profile".
Set deployment.forTests: true on the profile for your test engine. Or run in a terminal and answer y.
A step does not finish.
A step without a mock runs the real code. If no worker takes it within the timeout, the run fails and says what it was waiting for. Start the worker, or mock the step.
"No test-case files found."
Run penstock test-cases --generate . first.
The Run tests button is not there.
Run tests is shown for Camunda 7, Camunda 8, Operaton and CIB seven. Pin it from the More menu if you unpinned it.
The run left builds in my engine.
An interrupted run is cleaned up by the next run, once it is 15 minutes old.
