Editing a diagram

The editor is bpmn-js running in a JCEF browser inside the IDE window. The modelling surface is the familiar one. What Penstock adds is the IDE around it: a toolbar you arrange, a command palette over every action, a sidebar, and the raw XML never more than one click away.

The toolbar

One row across the top of the canvas, in one order in all three editors: undo, redo, the editor's own view switcher if it has one, its actions, the More button, Deploy as the one primary action, and the sidebar toggle at the right edge. Undo and redo are always on the bar. The sidebar toggle is an icon that stays pressed while the sidebar is open; Deploy is a button that opens a popover rather than deploying at once, which is described under Deployment.

The command palette

The More button, marked with three dots, opens a searchable list of every action, in sections, with the ones you used last first. The same list is Ctrl+Alt+,, or ⌥⌘, on a Mac, and the first-run tour names it. Type to filter: the letters you matched are marked in each row, and an action answers to keywords as well as to its name, so png finds Export, c8 finds what is Camunda 8, and bpmnlint finds Check. Each row has a pin.

The sections are the ones the menu is grouped under, in this order: Check and run, Layout and convert, Deploy and share, View, File, Edit, Help. See the table below for what is in each.

The same actions are in the IDE's own Find Action and Keymap under Tools | Penstock, so a shortcut can be bound to any of them the way the IDE binds its own. The palette's shortcut is Find Action in a diagram in the keymap, and Export keeps Cmd/Ctrl+Shift+C.

Pinning an action to the toolbar

The pin in each row of the palette, and of the More menu, puts that action on the toolbar or takes it off. The ones used often are pinned to start with; the rest are only in the menu. The choice is kept as the difference from those defaults in ~/.penstock/preferences.json, so it holds across IDEs and restarts, and an action added in a later release still shows up for someone who has arranged their toolbar. It is never written to penstock.yaml, because it is yours rather than the project's.

On the bar, an action that only a well known icon can name is an icon with a tooltip: undo, redo and the sidebar toggle. Everything else is a word. A toggle stays pressed while what it shows is open, and its label never changes with the state.

Canvas and palette

Which modeller is built depends on the engine profile. Camunda 7, Camunda 8, Operaton and CIB seven get the matching Camunda modeler, which carries that platform's moddle extensions, its properties provider and its element template support; Penstock adds the element template create and append module, and create and append anything to Camunda 8. Classic BPMN gets plain bpmn-js with the standard properties panel and provider, and now also the colour picker in the context pad and the grid with snapping, which the Camunda profiles already had. All of them load task resizing, token simulation and the minimap.

The palette is a floating island beside the canvas, not a strip of the window: sixteen pixels from the left edge, vertically centred, rounded, with a border and a shadow, and never more than three quarters of the height of the canvas, so a palette with more entries scrolls inside it. A canvas with a palette beside it is inset, so nothing sits under it, and a diagram is fitted into that inset when it opens. See BPMN elements for what is on it.

A diagram opens fitted into the canvas at 100% at most, rather than cut off at the edge. Opening a panel over a fitted diagram fits it again, unless you have moved or zoomed it yourself. Hovering an element for half a second shows a tooltip with its id, type, name and connected flows, plus the implementation, class or delegate expression on a service task, and the assignee and candidate users and groups on a user task. The right-click menu holds Reload, Undo, Redo, Copy, Paste, Delete and Export….

The properties panel

The properties of the selected element are the Properties tab of the sidebar, with the groups the engine profile defines. See The sidebar for how wide it is and what it remembers.

Editing scripts in an IDE tab

Under Camunda 7, script fields get a CodeMirror editor instead of a plain text area: Groovy highlighted as Groovy, everything else as JavaScript. It is installed into the Script and Condition groups and into the input mapping, output mapping, execution listener and task listener entries, so a script nested in a listener is edited like the task's own. Typing reaches the model 400 ms after you stop.

Below each editor is an Edit in new tab button. It hands the current text to the IDE, which opens it as an editor tab carrying the script format's extension - .groovy, or .js for JavaScript - so the IDE's own highlighting, completion and inspections apply. The file is in memory only; nothing is written to disk. While that tab is open the in-panel editor is read-only, so there is one place to type. Every keystroke in that tab is pushed back to the in-panel editor, debounced by 100 ms, and reaches the model on the same 400 ms rule as typing in the panel. Close the tab and the in-panel editor becomes editable again; press the button again and the existing tab is focused.

From a delegate class to the class

Right-click a task that names a Java class - a Camunda 7 camunda:class, a delegate expression that unwraps to a fully qualified name, a listener that names one - and the menu offers Go to that class. It opens the file in the IDE, found by name and package in the project's own sources. The entry appears only when the element actually names a class: a delegate expression that holds a bean name, such as ${checkStockDelegate}, names no class and is left alone. A class in a dependency rather than in the project's sources is not found. This is free.

The XML tab

The diagram editor is registered ahead of the IDE's own editor, not in place of it, so the plain XML editor stays available as a second tab on the same file, called Text. A diagram that cannot be read opens a screen of its own instead of an empty canvas: what the parser objected to and on which line, that the file was not changed, and buttons to open the XML in the Text tab at that line and to Reload.

Edits round-trip in both directions. Every change on the canvas re-serialises the diagram and writes the whole file: the content goes to a temporary file beside the target, which is moved over it atomically and refreshed in the VFS. There is no save step; the XML tab shows the new content at once, and a folder that does not exist yet is created.

The other direction is watched rather than merged. Penstock tracks the file's modification stamp and ignores its own writes. When something else changes the file - the XML tab, a Git checkout, a formatter - the editor asks whether to reload. Reloading takes the external content and discards unsaved canvas edits; declining keeps you editing, and your next change overwrites the external one. Renames are handled silently.

Copy, paste, undo and redo

Undo and redo drive the modeller's command stack, covering every modelling operation in the order it happened. Copy and paste go through the IDE's own CopyPasteManager - the system clipboard - rather than a clipboard private to one diagram, which is what makes copying a pool out of one diagram and pasting it into another open diagram work. Paste from the toolbar or the context menu, having no mouse position to attach to, drops the elements at the centre of the view.

Token simulation

Simulate switches the canvas into bpmn-js-token-simulation's simulation mode: the canvas is framed in green, every start event gains a play button, and the speed controls sit at the bottom. The button stays pressed until you switch it off. The module blocks dragging, the context pad, popup menus and direct editing, but not programmatic changes, so Penstock blocks the rest itself: Undo, Redo, Copy, Paste, Delete and Auto layout refuse to run and say Stop Token Simulation before editing the diagram. Otherwise an edit made during what looks like a read-only preview would be written to the file like any other. Free.

Transaction boundaries

Transaction boundaries, in the View section of the More menu, draws a bar where the engine commits a transaction. It draws one before a user task, a receive task, an event-based gateway, an external task, and a message, timer, signal or conditional catch event, and before or after any activity with an asynchronous continuation, multi-instance ones included. The bars follow the diagram as you edit it, take the accent colour of the theme, and each says Transaction boundary: the engine commits here when you rest the pointer on it.

Camunda 7, Operaton and CIB seven diagrams. Free. The behaviour is ported from camunda-transaction-boundaries, whose licence is in the third-party notices.

Export

Export… opens a large dialog with the whole diagram centred in the preview pane on the left and the settings on the right: Theme (Light, Dark, Dracula), Schema (Default, or Sketchy, which draws the diagram hand-drawn in the Virgil font), Format (SVG, PNG or PDF), a Use background checkbox, and, for a diagram with collapsed sub-processes, a choice of which one to export. The dialog opens light on white.

Along the bottom, in one row at the right, are Cancel, Copy and Save. Copy puts the diagram on the IDE clipboard as a PNG, drawn with the theme and background chosen there, ready to paste into Confluence, Slack or an e-mail. It is free, and there is no separate menu item for it any more. The picture is written by the IDE, since the browser clipboard is not available in the editor.

SVG is written as rendered. PNG is rasterised at twice the diagram's size, capped at 8192 pixels on the longer side so large diagrams stay inside the browser's canvas limit. PDF is that PNG on a single A4 page, portrait or landscape by aspect ratio, scaled to fit under a heading. Save then asks the IDE where to put the file.

Comparing two versions of a diagram

Penstock registers a diff tool with the IDE, so any two-sided comparison where one side is a BPMN file - Compare with Revision, a commit in the Git log, a shelved change - is shown as two diagrams rather than two blocks of XML: Before on the left, After on the right, each read-only, each centred in its own pane under a single title, with the palette and context pad hidden. The visual diff is part of Penstock Pro.

The comparison is semantic, not textual. Both revisions are parsed with bpmn-moddle and compared with bpmn-js-differ, which sorts elements into added, removed, changed, and changed in layout only. Each is outlined in its bucket's colour: removed on the Before side, added on the After side, changed on both.

The fourth bucket is the useful one. An element that only moved or was resized is marked in its own colour on the After side, apart from real changes, so a commit that ran auto layout reads as what it is rather than as every element having been edited.

The decision editor

A .dmn file opens in a decision editor in the same place, through the same shell: the requirements diagram, decision tables with their hit policy, typed inputs and outputs and a column for annotations, and literal and boxed expressions. The view switcher at the left of the toolbar switches between every decision in the file and between the requirements diagram and a table. Camunda's DMN extensions are read and kept, and the file is saved as you edit, the same as a diagram. The sidebar has Properties and Problems; see The sidebar.

DMN 1.1 and 1.2 files are converted to DMN 1.3 when they open, with @bpmn-io/dmn-migrate, and what the engine added to a decision is kept. A notice above the editor says the file will be saved as DMN 1.3 when you change it, and the file on disk is not touched until then. The command line does the same for penstock check, docs, share and migrate analyze, and a file that cannot be read is one finding with its file and line rather than a failed run.

Check in the decision editor compares the rules of every decision table: two rules of a Unique table that match the same input, which is an error at run time, rules of an Any table that do so with different results, and inputs no rule matches, naming the rules and a value both match. That is Pro. penstock check does the same for the .dmn files in a project. Deploy sends the file to the engine with the same settings a diagram uses, and the Penstock tool window lists decision files beside the processes.

The form editor

A Camunda Form, a .form file, opens in a form editor: the palette of fields beside the form, and the properties of the selected field in the Properties tab. It is saved as you edit and deployed with Deploy. A .form file of the IntelliJ GUI Designer is left to the GUI Designer. The sidebar has Properties, Preview and Problems; see The sidebar.

Check finds two fields writing one variable, or a field writing the path of a group - Tasklist refuses to open such a form - fields that write no variable, option lists that offer one value twice, and inputs with no label. The form check is free, in the editor and in penstock check alike, because it is lint. penstock docs writes a page per form with the variable every field writes, whether it is required, its options and when it is hidden. The decision editor's overlap and gap analysis stays Pro.
