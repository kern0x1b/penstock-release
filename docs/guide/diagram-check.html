Check and problems

Check asks three things about a diagram: can it be read, is it modelled correctly, and can the engine run it. The answers appear in two places - a short card over the canvas and the Problems tab of the sidebar, where the full list lives.

The check card

Press Check in the toolbar, or pick the Problems tab, and a card appears at the bottom right of the canvas. It is a summary: the counts in words, the first few findings, Recheck, Close, and Show all, which opens the Problems tab.

Each finding in the card is clickable, and the element it is about is outlined on the canvas. Everything the check found keeps an outline while the card is open, so the trouble is visible without reading a single line.

A small pill on the canvas carries the count, and the badge on the Problems tab carries it too. The pill is hidden while the card is open, since the card says the same thing, and both count the same findings. A compatibility rule the linter reports as information counts as a warning, and a problem two checks both report is counted once.

The Problems tab

The tab holds every finding, in groups, each with an error or a warning icon. It keeps its place while you look at another tab, so you can go to Properties to fix something and come back to the list. A tab with nothing to show says so and hints at what to do.

Clicking a finding selects its element on the canvas and opens the property that fixes it. That covers job type, form key or id, correlation key, history time to live, called element, error, escalation, message and signal references and timer definitions, and a missing job type, topic, class or delegate expression in the code. A finding with no single field still switches the sidebar to Properties and selects the element, so the next edit is one click away.

Every check has an id, and says why and how

Each check has a stable id - drawing/overlap, bpmnlint/label-required, form/key-clash - a line on why it matters and a line on how to fix it. Select a finding and the two lines appear under it, with a link to that check's own page. The same id travels with the finding everywhere else it is reported: penstock check --format json, SARIF and GitHub annotations all carry the id and its link, so a finding in a pull request leads back to the same page the editor showed.

The catalogue is generated from the rule definitions, so an id never changes meaning.

The groups

Drawing

What is wrong with how the diagram is drawn. These break the picture: a reader cannot tell what a diagram means when two shapes sit on top of each other, so they are listed first, with an error icon.

Shapes sit on top of each otherTwo shapes overlap. Neither can be read, and a click lands on whichever happens to be on top.
Connection runs through a shapeA line crosses the interior of a shape it does not connect, so it reads as though it stops there.
Connection does not reach the shape it connectsThe line ends short of, or past, the element it is attached to. Usually the result of moving a shape without the line following it.
Element outside the container it belongs toAn element is drawn outside the pool, lane or sub-process that owns it in the model, or inside one that does not.
Boundary event is off its hostA boundary event is no longer on the border of the activity it is attached to.
Labels cover each otherTwo labels overlap, so at least one of them cannot be read.
Connection doubles back along itselfA route leaves a point, goes past it and comes back along the same line. It reads as a single line drawn twice.

How it runs

Pro, and Team in a pipeline. Flow analysis follows every way a token can take from each start event and reports what goes wrong on the way. Each finding names the cause, and clicking it outlines the path that leads there on the diagram.

The process can get stuckA gateway waits for something that never comes - usually a parallel gateway joining branches an exclusive gateway chose between, or a boundary event that took the run somewhere else.
A part of the process can run twiceBranches that run at the same time meet at an exclusive gateway or a task, so everything after it runs once per branch.
An element can never runNothing leads to it, or every way to it is closed off.
The process may never finishOnce it gets to a certain point, no path leads to an end: it can only go round.
A decision has no way out for some valuesA gateway without a default flow whose conditions leave a value uncovered - amount > 100 and amount < 100 stop at exactly 100 - so the process stops there with an incident.
Two ways out of a decision can both holdTwo conditions of an exclusive gateway overlap, and the engine takes whichever it checks first.
Two variables look like oneNames that differ only by letter case or one character, such as orderId and orderID: one of them is probably a typo.

Without Pro the group says how many such problems it found and offers to buy it. The same analysis is the flow section of penstock check, or penstock check --only flow on its own.

Engine

Free. This is what the engine the diagram is written for cannot run, taken from bpmnlint-plugin-camunda-compat: a service task with no job type, an element or an expression the chosen version cannot run, a process with no history time to live. Sixty rules, each with an id such as compat/implementation.

They run against the version in the file's modeler:executionPlatformVersion, or the newest one when the file has none, and against the engine penstock.yaml names. Operaton and CIB seven are checked as Camunda 7.

Each finding is a plain sentence naming the element: Charge card has no job type, Ad-hoc sub-processes need Camunda 8.7 or newer - this diagram targets 8.6, History time to live is missing. The same sentence is used in the card, on the canvas, in penstock check, in SARIF and in GitHub annotations, so it reads the same wherever you meet it.

In a .bpmnlintrc a compatibility rule is turned off as camunda-compat/<rule>, the plugin's own name, or as compat/<rule>. A problem another check already reports on the same element - two blank start events, a link event name used twice - is shown once, by bpmnlint. See Validation.

Rules

What bpmnlint reports, with the project's .bpmnlintrc or, when there is none, bpmnlint:recommended. A rule set to warn is marked as a warning and is not counted as an error in the header. If the rules cannot run, the group says why instead of staying empty. See Validation.

Code

Where a diagram and the code that runs it disagree: a service task, listener or external task whose job type, topic, class or Spring bean has nothing in the project to run it, a call activity that calls a process no diagram defines, a business rule task whose decision no .dmn file defines, a user task whose form no .form file provides, and a worker no diagram uses. Each finding has the file and the line, and the IDE opens it there. This is part of the link between diagrams and code, so it is Pro.

Migrate to Camunda 8

For a Camunda 7, Operaton or CIB seven diagram only, a group of its own with the result of the migration analysis, grouped by diagram, decision and form, and a Convert action. See Camunda 7 to Camunda 8.

Readability

The last group is collapsed, and deliberately so: a diagram drawn by hand always has some of these, and a count of zero is not the goal. They are worth reading when a diagram is hard to follow and you want to know why.

Connections crossTwo lines cross each other.
Connections run along the same lineTwo lines run parallel close enough to be read as one.
Connection runs along the border of a shapeA line runs beside a shape's edge for long enough to look attached to it.
Connection crosses a labelA line is drawn over a label that belongs to something else.
Connection takes a long way roundThe route is more than twice the distance between the two shapes it connects.
Connection sidesteps for no reasonA short jog between two parallel runs with nothing in the way of the straight line.
Label sits far from what it namesA label has drifted away from its shape or its own line.
Annotation sits far from what it describesA text annotation is joined to its element by an unusually long association.
Connection is not drawn at right anglesA segment runs diagonally rather than horizontally or vertically.

Decisions and forms

The decision and form editors have a Problems tab of their own, and it is the same list for one file. For a .dmn file it is the decision check: rules of a Unique table that match the same input, which is an error at run time, rules of an Any table that do so with different results, and inputs no rule matches, each naming the rules and a value both match. That is Pro.

For a .form file it is the form check: two fields writing one variable, or a field writing the path of a group, which Tasklist refuses to open, fields that write no variable, option lists offering one value twice, and inputs with no label. The form check is free, in the editor and in penstock check alike, because it is lint.

On the command line

penstock check reports everything in one run, in sections: the drawing, the rules, the engine compatibility rules, and on Pro how the processes, decisions and forms run. --only drawing,rules,flow narrows it. The exit code is what makes a build fail, and a baseline makes it fail only on what is new. See Command line.

Fixing a whole diagram at once

Auto layout is the other half of this. The check measures a diagram against a set of rules; auto layout draws a diagram that satisfies them. On a diagram that has drifted far enough to collect a long list of drawing problems, laying it out again is usually faster than working down the list by hand.

What it cannot see

Three measures need the file rather than the canvas - a connection declared in the XML that was never drawn, one drawn with an end missing, and a comparison of what the diagram meant before an operation against what it means after. The check leaves those out rather than reporting them as passing. A diagram that cannot be read shows its own screen instead of a card: the parser's line, that the file was not changed, and a button that opens the XML in the Text tab at that line, with Reload beside it.
