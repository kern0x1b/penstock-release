Deployment

Deploy is one click and then one more. It sends the diagram you are editing, the decision or the form, to the engine penstock.yaml points at, and asks for the engine address and the sign-in the first time. The request is made by the IDE process, not by the embedded browser, so no CORS configuration is needed on the engine. Secrets go to the IDE password safe, never to a project file.

The Deploy popover

Deploy sits at the right of the editor toolbar, as the one primary action, when the file's engine profile has an engine behind it: Camunda 7, Camunda 8, Operaton or CIB seven. Under the Classic BPMN 2.0 profile there is no deployment target and the button is not shown. See Engine profiles.

Pressing it opens a popover under the button rather than deploying at once. The popover tells you three things and offers two actions:

ProfileWhich one is in force, and every other profile in the file, so a diagram can go to staging without changing what is in force
Engine addressWhere it will go, or Not set yet
What will be sentThe files, by name, with a count for the rest. For a diagram that is the diagram and nothing else
Edit connection…Opens the Connection dialog for the profile you picked
DeploySends, to the profile you picked

It sends the current state of the canvas, including edits that have not reached the disk yet. The result is a notification: where the diagram went, or what the engine answered. The DMN and form editors have the same button, and the tool window's Deploy sends every diagram in a folder to its profile after asking.

The Connection dialog

The dialog opens from Edit connection… in the popover, and it opens by itself the first time you deploy to a profile that has no engine address, or whose sign-in has no password or client secret stored yet. Its title names the engine and the profile, such as Camunda 8 · prod.

Engine addressThe Camunda 7 REST API, such as http://localhost:8080/engine-rest, which is what Operaton and CIB seven answer on as well, or the Camunda 8 REST address, such as http://localhost:8088. Required, http or https
Sign inNot needed, User and password, or OAuth client
User, PasswordFor User and password, sent as Authorization: Basic
Client id, Client secret, Token address, AudienceFor OAuth client: the client credentials grant. The audience is optional

Opened from Edit connection…, the dialog offers Save, which only saves, and Save and deploy. Opened by a deploy, because nothing is set up yet, it offers Save and deploy alone.

The address and the sign-in type, user name, client id, token address and audience go to penstock.local.yaml, under the profile's name when a profile is in force, which stays on this machine; see Configuration. The password or client secret goes to the IDE password safe, separately for each profile, and the dialog only says that one is stored rather than reading the value back out. Leaving the field empty keeps the stored one, and typing replaces it. Saving with Sign in set to Not needed removes it.

What is set in penstock.yaml

Everything else about a deployment is part of the project, not the dialog: the deployment name, the tenant, the source, the activation time and whether to leave out what the engine already has. A profile overrides any of it for another environment.

deployment:
  url: http://localhost:8080/engine-rest
  name: Order handling
  tenantId: orders
  changedOnly: true

profiles:
  prod:
    deployment:
      url: https://bpm.example.com/engine-rest
      auth:
        type: oauth
        clientId: penstock
        tokenUrl: https://auth.example.com/oauth/token

hooks:
  preDeploy: npm run verify-workers
  postDeploy: ./notify-release.sh
nameDefaults to Penstock deployment, so the engine's duplicate check can match one deployment to the next
sourceDefaults to penstock
tenantIdEmpty means the default tenant
changedOnlyLeaves out what the engine already has unchanged. On unless set to false
forTestsMarks an engine that test-case runs may deploy to and answer jobs on. See The sidebar
activationTimeAn ISO 8601 timestamp. Empty means activate immediately. Camunda 7 family

What is sent

The diagram goes to the engine as one multipart/form-data POST carrying a single file part named after the file, with content type application/xml (application/json for a form). Nothing else from the project is included - no other diagrams, no element templates, no settings file. OAuth is the one case that makes a second request: the token request that precedes the deployment.

Camunda 7, Operaton, CIB seven/deployment/create is appended to the address. The deployment name, source, tenant and activation time go as form fields beside the file, and changedOnly sets both enable-duplicate-filtering and deploy-changed-only
Camunda 8/v2/deployments is appended to the address; an address that already ends in /v2 works as well. The file goes as resources, with tenantId beside it when one is set

penstock deploy on the command line uses the same addresses and the same settings, and sends the diagrams, decisions and forms together grouped by the target each folder asks for, so the IDE and a pipeline mean the same thing by deployment.url. See Command line.

OAuth

With OAuth client, Penstock first POSTs grant_type=client_credentials with the client id and secret to the token address as a form-encoded body, reads access_token out of the JSON response, and uses it as a bearer token on the deployment request. If the token endpoint cannot be reached, answers with a non-2xx status, or returns a body without an access token, the deployment stops there and the error says which of the three happened. The audience is sent only when you fill it in. The token request has its own 15-second timeout.

Hooks

preDeploy and postDeploy in penstock.yaml run around a deployment from the IDE, as they do on the command line. They run in the project root with PENSTOCK_FILES - one file per line - PENSTOCK_ROOT, PENSTOCK_STAGE and PENSTOCK_PROFILE set. A preDeploy that fails stops the deployment and nothing is sent; postDeploy runs after a successful one.

Hooks run only in a trusted project. In a project the IDE does not trust, a configured preDeploy is not run, and the deployment stops rather than go ahead without it.

What the engine says

A successful deployment names the file and the address it went to.

A deployment the engine refuses says which files it refused and why, one line for each, in the editor and in penstock deploy, rather than repeating the engine's raw list of element errors. An answer of 401 or 403 offers Edit connection in the editor's message; penstock deploy says what to set, which is deployment.auth in penstock.local.yaml, or PENSTOCK_PASSWORD, PENSTOCK_CLIENT_SECRET or PENSTOCK_TOKEN. A request that never reached the engine says Could not reach the engine at <url>, and a deployment with no address anywhere says so and points at deployment.url or the Connection dialog. The request times out on its own after 30 seconds, and the connection after 10.

Before anything is sent, penstock deploy and penstock doctor say so when deployment.auth.type is basic and there is no PENSTOCK_PASSWORD, rather than letting the engine refuse it.

How a dialog is put together

Every dialog, popover and form in the editor follows one standard, and the Connection dialog is one of them: the same sizes, the same footer, the same focus and Esc behaviour, labels without a colon, help as permanent text under the field rather than a tooltip, and an error as text under the field with a red outline once you have left it. Export, the import report, Run with input, Save as scenario, Open run and the connector template browser use the same one. The buttons of a dialog follow the IDE: the primary button is on the right on macOS and first on Windows and Linux.

Security

Deployment is the only thing that sends a diagram off the machine. The plugin makes no other outbound call of its own apart from the licence check, which talks to the licence service about the licence and nothing else, and the connector template download described under Element templates. No telemetry, no update polling. A command-line action run from the Penstock tool window downloads the penstock CLI the first time it needs a version it does not have yet. A diagram leaves the machine only when you press Deploy, and only to the address configured for the profile.

Because secrets are held by the IDE password safe, nothing a deployment needs to sign in is committed with the project. The address typed into the Connection dialog stays in penstock.local.yaml, which Penstock adds to .gitignore when the project has one. A password: key in penstock.local.yaml is not read; a password comes from PENSTOCK_PASSWORD or from the IDE password safe.

There is no option to skip certificate validation, and none is planned. An engine behind a self-signed or private certificate has to be trusted by the Java runtime the IDE is using.
