Deployment

Deploy is one click. It sends the diagram you are editing to the engine penstock.yaml points at - the profile in force, with its deployment name, tenant and hooks - and asks only for the engine address and the sign-in, the first time. The request to the engine is made by the IDE process, not by the embedded browser, so no CORS configuration is needed on the engine. Secrets go to the IDE password safe, never to a project file.

Deploying

The Deploy button sits at the right of the editor toolbar when the diagram's engine profile is Camunda 7 or Camunda 8. Under the Classic BPMN 2.0 profile there is no deployment target, so the button is not shown. See Engine profiles for how the profile is chosen. The DMN and form editors have the same button.

Pressing Deploy sends the current state of the canvas, including edits that have not reached the disk yet, to the profile in force. Its tooltip names the address it will use. A message says where the diagram went, or what the engine answered.

The arrow next to Deploy opens a short menu. When penstock.yaml defines profiles, it has a Deploy to <profile> entry for each of them, and Deploy to default for the plain settings, so a diagram can go to staging without changing which profile is in force. Connection… edits the engine address and the sign-in of the profile in force.

The Connection dialog

The first time you deploy to a profile that has no engine address, or whose sign-in has no password or client secret stored yet, the Connection dialog opens instead. Its title names the engine and the profile, such as Camunda 8 · prod.

Engine addressThe Camunda 7 REST API, such as http://localhost:8080/engine-rest, or the Camunda 8 REST address, such as http://localhost:8088. Required, http or https
Sign inNot needed, User and password, or OAuth client
User, PasswordFor User and password, sent as Authorization: Basic
Client id, Client secret, Token address, AudienceFor OAuth client: the client credentials grant. The audience is optional

Save and Deploy keeps what you entered and deploys. The address and the sign-in type, user name, client id, token address and audience go to penstock.local.yaml, under the profile's name when a profile is in force, which stays on this machine; see Configuration. The password or client secret goes to the IDE password safe, separately for each profile.

What is set in penstock.yaml

Everything else about a deployment is part of the project, not the dialog: the deployment name, the tenant, the source, the activation time and whether to leave out what the engine already has. A profile overrides any of it for another environment. 

deployment:
  url: http://localhost:8080/engine-rest
  name: Order handling
  tenantId: orders
  changedOnly: true

profiles:
  prod:
    deployment:
      url: https://bpm.example.com/engine-rest
      auth:
        type: oauth
        clientId: penstock
        tokenUrl: https://auth.example.com/oauth/token

hooks:
  preDeploy: npm run verify-workers
  postDeploy: ./notify-release.sh
nameDefaults to Penstock deployment, so the engine's duplicate check can match one deployment to the next
sourceDefaults to penstock
tenantIdEmpty means the default tenant
changedOnlyLeaves out what the engine already has unchanged. On unless set to false
activationTimeAn ISO 8601 timestamp. Empty means activate immediately. Camunda 7

What is sent

The diagram goes to the engine as one multipart/form-data POST carrying a single file part named after the file, with content type application/xml (application/json for a form). Nothing else from the project is included - no other diagrams, no element templates, no settings file. OAuth is the one case that makes a second request: the token request that precedes the deployment.

Camunda 7/deployment/create is appended to the address. The deployment name, source, tenant and activation time go as form fields beside the file, and changedOnly sets both enable-duplicate-filtering and deploy-changed-only
Camunda 8/v2/deployments is appended to the address; an address that already ends in /v2 works as well. The file goes as resources, with tenantId beside it when one is set

penstock deploy on the command line uses the same addresses and the same settings, so the IDE and a pipeline mean the same thing by deployment.url. See Command line.

OAuth

With OAuth client, Penstock first POSTs grant_type=client_credentials with the client id and secret to the token address as a form-encoded body, reads access_token out of the JSON response, and uses it as a bearer token on the deployment request. If the token endpoint cannot be reached, answers with a non-2xx status, or returns a body without an access token, the deployment stops there and the error says which of the three happened. The audience is sent only when you fill it in. The token request has its own 15-second timeout.

Hooks

preDeploy and postDeploy in penstock.yaml run around a deployment from the IDE, as they do on the command line. They run in the project root with PENSTOCK_FILES, PENSTOCK_ROOT, PENSTOCK_STAGE and PENSTOCK_PROFILE set. A preDeploy that fails stops the deployment, and nothing is sent; postDeploy runs after a successful one.

Hooks run only in a trusted project. In a project the IDE does not trust, a configured preDeploy is not run, and the deployment stops rather than go ahead without it.

Feedback

A message appears in the editor while the request is in flight, and again when it finishes. A successful deployment names the file and the address it went to.

If the engine rejects the deployment, the message carries the address, the HTTP status code and the engine's own message from its response, which is where the useful detail usually is. A request that never reached the engine says Could not reach the engine at <url>. A deployment with no address anywhere says so and points at deployment.url or the Connection dialog. The request times out on its own after 30 seconds, and the connection after 10.

Security

Deployment is the only thing that sends a diagram off the machine. The plugin makes no other outbound calls of its own apart from the licence check, which talks to the licence service about the licence and nothing else - no telemetry, no update polling. A command-line action run from the Penstock tool window downloads the penstock CLI the first time it needs a version it does not have yet. The element template catalogue the editor shows is read from files bundled with the plugin. A diagram leaves the machine only when you press Deploy, and only to the address configured for the profile.

Because secrets are held by the IDE password safe, nothing a deployment needs to sign in is committed with the project. The address typed into the Connection dialog stays in penstock.local.yaml, which Penstock adds to .gitignore when the project has one.
