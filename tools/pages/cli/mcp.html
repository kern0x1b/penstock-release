What it is

MCP (Model Context Protocol) is a way for an AI assistant to use a program's tools. penstock mcp starts a small server on your machine that talks to the assistant over standard input and output. It offers fourteen tools, the diagrams of the open folders as resources, and two prompts. It reads BPMN diagrams, DMN decision files and Camunda forms. An assistant that edits a diagram can check straight away that it still runs to its end.

Connect an AI assistant

The CLI needs Node.js. Node.js 22.22 or later must be on the PATH of your assistant. The tools that read, check, search, compare and draw are free, with no time limit: list_diagrams, show_diagram, element_context, check_diagram, search_elements, diff_diagrams and export_image. The other tools are part of Penstock Pro, and Team in a pipeline, as penstock mcp --help states.

Running penstock mcp --config prints the standard client configuration. There is no project folder in the entry: you configure it once, and the server finds each project from the files the assistant asks about. The entry names the exact version of the command line that printed it, as npx --yes @kern0x1b/penstock-cli@<version> mcp, so the assistant runs the version you have. A development build of the command line has no published version, and prints penstock mcp instead. The entries below, written by hand, run whatever version npm serves; paste the printed one to pin it. With the command line installed (npm install -g @kern0x1b/penstock-cli), claude mcp add penstock -- penstock mcp adds it to Claude Code.

Two other ways to give an agent the tools need no entry in its settings. penstock agent claude, codex, gemini or opencode starts that agent in your terminal with the server set up for that one run and nothing written to the agent's configuration. See agent. And the AI chat in the Penstock editors starts your agent with the same server, so it reads diagrams, rules, scenarios and code links as the command line does.

penstock mcp --project <dir> fixes the project: every tool works on that folder, the assistant does not have to name it, and nothing outside it is read.

Claude Code

Run this command in your terminal:

claude mcp add penstock -- npx --yes @kern0x1b/penstock-cli mcp

Claude Desktop

In claude_desktop_config.json (under ~/Library/Application Support/Claude/ on macOS or %APPDATA%\Claude\ on Windows), add penstock under mcpServers:

{
  "mcpServers": {
    "penstock": {
      "command": "npx",
      "args": ["--yes", "@kern0x1b/penstock-cli", "mcp"]
    }
  }
}

Cursor

In .cursor/mcp.json in your project, or in ~/.cursor/mcp.json for all projects, add the server under mcpServers:

{
  "mcpServers": {
    "penstock": {
      "command": "npx",
      "args": ["--yes", "@kern0x1b/penstock-cli", "mcp"]
    }
  }
}

VS Code

In VS Code 1.101 or later with GitHub Copilot agent mode, the Penstock extension registers the MCP server automatically in trusted workspaces when Node.js and npm are on the PATH. The extension launches ./penstockw mcp if the project has the wrapper, or npx @kern0x1b/penstock-cli mcp if not.

For manual setup in .vscode/mcp.json, VS Code uses the servers key and requires type: "stdio" rather than mcpServers:

{
  "servers": {
    "penstock": {
      "type": "stdio",
      "command": "npx",
      "args": ["--yes", "@kern0x1b/penstock-cli", "mcp"]
    }
  }
}

JetBrains AI Assistant and Junie

{
  "mcpServers": {

      "command": "npx",

For JetBrains Junie, add the entry under mcpServers in ~/.junie/mcp/mcp.json (global) or .junie/mcp/mcp.json (project root), or configure it in Settings | Tools | Junie | MCP Settings.

How the server finds your project

The server serves diagrams across projects. For each request it starts from the file or folder the assistant names, walks up to the nearest penstock.yaml (or the repository root), and uses that project's engine, settings and conventions.

Kind of toolHow you point it at a project
Tools that read any kind of file: show_diagram, element_context, check_diagramThe assistant passes the absolute path of a .bpmn, .dmn or .form file, in file.
BPMN-only tools: analyze_flow, list_scenarios, edit_diagram, layout_diagram, export_image, diff_diagramsThe assistant passes the absolute path of a .bpmn or .bpmn20.xml file, in file. diff_diagrams also takes a second file in other.
Whole-project tools: list_diagrams, search_elements, check_code_links, run_scenariosThe assistant passes an absolute folder in the optional project. Without it, the tool uses the folders the AI client has open. run_scenarios also takes a single diagram in file.

The folders the client has open (MCP roots)

Many AI clients tell the server which folders are open in their workspace. MCP calls these roots. When the client does, the server:

  • uses those folders as the default projects for the whole-project tools,
  • updates the list when the client says the folders changed,
  • refuses any file or folder outside them, so the assistant cannot read outside the workspace it was given.

When the client sends no roots, the whole-project tools need an explicit absolute project. The file tools then accept any valid diagram whose path resolves to a project.

The tools

list_diagramsLists the BPMN diagrams, DMN decision files and Camunda forms of a project, as absolute paths, each with its kind: process, decision or form.Free
show_diagramDescribes a file. For a BPMN diagram: every element and flow with id, type, name, connections and engine properties. Read this before editing. Edits refer to these ids. For a DMN file: each decision with its hit policy, inputs, outputs, rules and the decisions, input data and knowledge it requires. element_contextSays what surrounds one element: the variables that reach it, what it reads and writes, its job types, and the job types, processes and decisions the project already uses. For a form it reports duplicate or missing keys, and for a DMN file one that cannot be read, free of charge. Gaps and overlaps between the rules of a decision table need Pro, and Team in a pipeline; without it the answer says they were left out.Free
search_elementsFinds where a name is used across the project, by id or name and ignoring case: elements, processes, messages, decisions and their outputs, variables with the elements that write and read them, and form fields. It takes query and the optional project, kinds and limit.Free
diff_diagramsSays what changed between two BPMN diagrams, or between a diagram and its committed version (HEAD, or the revision in ref): the elements added, removed and changed, and the ids of those that only moved on the canvas.Free
export_imageDraws a BPMN diagram as SVG, returned as text, or as PNG, returned as an image. PNG needs puppeteer installed, as penstock export does. With out, an absolute folder, the file is written there instead.Free
analyze_flowFinds deadlocks, branches that run twice, elements that never run and loops with no way out, with the path of ids that leads there. Run it after edit_diagram.Pro, Team in a pipeline
list_scenariosLists every distinct way through a diagram: the decisions taken, their conditions, the steps and where it ends.Pro, Team in a pipeline
check_code_linksChecks every diagram against the code, with file and line.Pro, Team in a pipeline
edit_diagramChanges a diagram through the editor's own modelling. Operations apply together or not at all. An edit that would break the drawing is refused, and so is a write over a diagram that changed on disk while the edit was made. dryRun shows the result without writing. It edits BPMN diagrams only.Pro, Team in a pipeline
layout_diagramRuns the editor's auto layout on a BPMN diagram and writes the result in one atomic step. Elements and flows stay the same; only positions change. dryRun lists the elements that would move without writing.Pro, Team in a pipeline
run_scenariosRuns the saved test cases of a project, or of one diagram, as penstock scenarios run does, and returns which passed, failed or were skipped. The engine must be marked for tests. Traces are kept under .penstock/runs.Pro, Team in a pipeline
test_taskRuns one element of a diagram on the local engine the project marks for tests, as penstock test task does: the process is deployed as a test build, the path to the element is completed or mocked, then the element is completed, made to throw a BPMN error or left waiting. It returns the state of the element, what it received and sent, the variables, the incidents and the state of the instance, and removes the build. It takes file and element, and the optional variables, complete, error, hold, process and timeout. Use only one of complete, error and hold. Traces are kept under .penstock/runs.Pro, Team in a pipeline

edit_diagram takes file, operations and the optional dryRun. The operations are the same contract as penstock edit --ops: add, connect, set, remove and move, which shifts an element by dx and dy. A business rule task names its decision with decisionRef on Camunda 7, Operaton and CIB seven, and with decisionId on Camunda 8. penstock edit <file> --schema prints the contract for the file's engine. The whole-project tools take project. The others take file.

Resources and prompts

Besides tools, the server lists the diagrams, decision files and forms of the folders the client has open as MCP resources, each with its kind, and returns the text of one when the client reads it. Clients that show resources let you attach a diagram to a conversation without a tool call. Paths outside the open folders are refused, as for the tools. Without roots nothing is listed.

Two prompts are offered, both taking file: review_diagram asks the assistant to read a file, run the checks and list what to fix, most serious first, without editing; explain_process asks it to explain a process in plain language from its scenarios. Resources and prompts are free.

A tool that needs a licence you do not have appears in the tool list with a note on what it needs. Called without the licence, it says so in its error result, with how to buy or sign in. In a pipeline the paid tools need Team. See Plans and licence.

A result is bounded. When it is longer than 100,000 characters it is cut and says The result was cut at 100000 of … characters. Ask for less: one process, or a smaller diagram.

Safety

  • The server runs on your machine. Nothing is sent anywhere by it. See Security and privacy.
  • When the client gives roots, paths outside them are refused. Files that are not .bpmn, .bpmn20.xml, .dmn or .form files are refused too.
  • An assistant can change a diagram only with edit_diagram and layout_diagram, and write an image only with export_image when it passes out. run_scenarios writes its traces under .penstock/runs and runs only on an engine marked for tests. Ask the assistant to use dryRun first, and keep your diagrams in Git so you can review the diff. A diagram that changed on disk while an edit was being made is never overwritten: the tool answers The diagram changed while the edit was being made, so it was not written over.

What you see

  • The assistant lists the tools. Paid tools show a note on what they need.
  • A tool call returns JSON, or a plain error message that says what is wrong.

Common problems

The assistant does not see the tools.
Check the command and args in the entry. Node.js 22.22 or later must be on the PATH of the assistant. Run penstock mcp by hand: it should wait silently for input.
"must be an absolute path to a diagram" or "\"project\" must be an absolute path".
The tools take absolute paths. Ask the assistant to pass the full path, as list_diagrams prints it.
"is outside the workspace roots".
The path is not inside a folder the client has open. Open the project in the client, or give a path inside an open folder.
"is not a Penstock project".
The folder has no penstock.yaml and no repository root above it. Run penstock init there.
A paid tool says it needs a licence.
Sign in on the machine that runs the server: penstock license login.
