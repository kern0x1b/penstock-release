What it is

MCP (Model Context Protocol) is a way for an AI assistant to use a program's tools. penstock mcp starts a small server on your machine that talks to the assistant over standard input and output. It offers thirty tools, the diagrams of the open folders as resources, and two prompts. It reads BPMN diagrams, DMN decision files and Camunda forms. An assistant that edits a diagram can check straight away that it still runs to its end.

Connect an AI assistant

The CLI needs Node.js. Node.js 22.22 or later must be on the PATH of your assistant. The tools that read, check, search, compare, analyse for Camunda 8 and draw are free, with no time limit: list_diagrams, show_diagram, element_context, check_diagram, search_elements, diff_diagrams, migrate_analyze, export_image, connections, agents, drift (for one environment), import_diagram, refactor_rename, test_dmn (up to 3 cases per decision) and the previews of migrate_agents and incident_to_scenario. The other tools, and the writes behind the free ones, are part of Penstock Pro, and Team in a pipeline, as penstock mcp --help states.

Running penstock mcp --config prints the standard client configuration. There is no project folder in the entry: you configure it once, and the server finds each project from the files the assistant asks about. The entry names the exact version of the command line that printed it, as npx --yes @kern0x1b/penstock-cli@<version> mcp, so the assistant runs the version you have. A development build of the command line has no published version, and prints penstock mcp instead. The entries below, written by hand, run whatever version npm serves; paste the printed one to pin it. With the command line installed (npm install -g @kern0x1b/penstock-cli), claude mcp add penstock -- penstock mcp adds it to Claude Code.

Two other ways to give an agent the tools need no entry in its settings. penstock agent claude, codex, gemini or opencode starts that agent in your terminal with the server set up for that one run and nothing written to the agent's configuration. See agent. And the AI chat in the Penstock editors starts your agent with the same server, so it reads diagrams, rules, scenarios and code links as the command line does.

penstock mcp --project <dir> fixes the project: every tool works on that folder, the assistant does not have to name it, and nothing outside it is read.

Claude Code

Run this command in your terminal:

claude mcp add penstock -- npx --yes @kern0x1b/penstock-cli mcp

Claude Desktop

In claude_desktop_config.json (under ~/Library/Application Support/Claude/ on macOS or %APPDATA%\Claude\ on Windows), add penstock under mcpServers:

{
  "mcpServers": {
    "penstock": {
      "command": "npx",
      "args": ["--yes", "@kern0x1b/penstock-cli", "mcp"]
    }
  }
}

    }
  }
}

VS Code

In VS Code 1.101 or later with GitHub Copilot agent mode, the Penstock extension registers the MCP server automatically in trusted workspaces when Node.js and npm are on the PATH. The extension launches ./penstockw mcp if the project has the wrapper, or npx @kern0x1b/penstock-cli mcp if not.

For manual setup in .vscode/mcp.json, VS Code uses the servers key and requires type: "stdio" rather than mcpServers:

{
  "servers": {
    "penstock": {
      "type": "stdio",
      "command": "npx",
      "args": ["--yes", "@kern0x1b/penstock-cli", "mcp"]
    }
  }
}

How the server finds your project

The server serves diagrams across projects. For each request it starts from the file or folder the assistant names, walks up to the nearest penstock.yaml (or the repository root), and uses that project's engine, settings and conventions.

Kind of toolHow you point it at a project
Tools that read any kind of file: show_diagram, element_context, check_diagram, diff_diagramsThe assistant passes the absolute path of a .bpmn, .dmn or .form file, in file. diff_diagrams also takes a second file of the same kind in other.
BPMN-only tools: analyze_flow, list_scenarios, edit_diagram, layout_diagram, export_imageThe assistant passes the absolute path of a .bpmn or .bpmn20.xml file, in file.
Whole-project tools: list_diagrams, search_elements, check_code_links, run_scenarios, migrate_analyzeThe assistant passes an absolute folder in the optional project. Without it, the tool uses the folders the AI client has open. run_scenarios and migrate_analyze also take a single file in file; migrate_analyze takes either file or project, not both.
The tool that makes a file: create_diagramThe assistant passes the absolute path of the new .bpmn, .dmn or .form file, in file. The path must not exist yet.

The folders the client has open (MCP roots)

Many AI clients tell the server which folders are open in their workspace. MCP calls these roots. When the client does, the server:

  • uses those folders as the default projects for the whole-project tools,
  • updates the list when the client says the folders changed,
  • refuses any file or folder outside them, so the assistant cannot read outside the workspace it was given.

When the client sends no roots, the whole-project tools need an explicit absolute project. The file tools then accept any valid diagram whose path resolves to a project.

Receipts and the scenarios argument

Whenever an agent changes project files through one of the writing tools (edit_diagram, layout_diagram, create_diagram, migrate_apply, migrate_agents, refactor_*, generate_templates, incident_to_scenario and the saving of a case by test_dmn), Penstock records what changed and returns it in the receipt field of the result: each file with a SHA-256 before and after, the diff in the diagram's own terms, the Check result before and after with the new findings named by rule and element id, and a verdict (verified, has new findings, or not verified with the reason). It holds names, hashes and ids, never file contents or secret values. With Penstock Pro, new Check errors are handed back to the agent in the tool result, up to ai.verify.attempts times (3 by default, 0 turns it off). The saved scenarios of a change run only with scenarios: true, and only on an engine marked deployment.forTests. See AI receipt and auto-repair.

The spec of create_diagram

Without spec the file is empty, for the engine in penstock.yaml. name is the name of the diagram, the file name by default. description is the documentation of a BPMN process, or the description of a DMN decision; a form has none, and a description for one is refused. A spec that has an unknown key, or a value of the wrong kind, is refused with the place named, and nothing is written.

FileThe spec
.bpmnExactly one of two keys. steps is a list of elements in a line, each after the one before and the first after the start event. A step has element (one of task, user-task, service-task, script-task, send-task, receive-task, business-rule-task, manual-task, call-activity, sub-process, end-event, intermediate-catch-event, intermediate-throw-event, exclusive-gateway, parallel-gateway, inclusive-gateway or event-based-gateway) and the optional name, event (message, timer, signal, error, escalation, conditional or terminate), id (Step_<n> by default) and properties. operations is a list of the operations of edit_diagram, applied to the empty diagram.
.dmninputs, a list with expression and the optional label and typeRef; outputs, a list with name and the optional label and typeRef; the optional hitPolicy (UNIQUE by default, FIRST, PRIORITY, ANY, COLLECT, RULE ORDER or OUTPUT ORDER); and the optional rules, each with when (one text for each input, in order), then (one text for each output) and an optional description. typeRef is string (the default), number, boolean, integer, long, double, date, time or dateTime.
.formfields, a list. A field has type: textfield, textarea, number, checkbox, checklist, radio, select, taglist, datetime, text or button. An input field has a key, unique in the form, and the optional label and required. A checklist, radio, select or taglist also has options, each with label and value. A text field has text. A button has label and submits the form.
 
{
  "file": "/work/shop/src/main/resources/ship-order.bpmn",
  "spec": {
    "steps": [
      { "element": "service-task", "name": "Reserve stock" },
      { "element": "user-task", "name": "Pack the order" },
      { "element": "end-event", "name": "Order shipped" }
    ]
  }
}

Resources and prompts

Besides tools, the server lists the diagrams, decision files and forms of the folders the client has open as MCP resources, each with its kind, and returns the text of one when the client reads it. Clients that show resources let you attach a diagram to a conversation without a tool call. Paths outside the open folders are refused, as for the tools. Without roots nothing is listed.

Two prompts are offered, both taking file: review_diagram asks the assistant to read a file, run the checks and list what to fix, most serious first, without editing; explain_process asks it to explain a process in plain language from its scenarios. Resources and prompts are free.

A tool that needs a licence you do not have appears in the tool list with a note on what it needs. Called without the licence, it says so in its error result, with how to buy or sign in. In a pipeline the paid tools need Team. See Plans and licence.

A result is bounded. When it is longer than 100,000 characters it is cut and says The result was cut at 100000 of … characters. Ask for less: one process, or a smaller diagram.

Safety

  • The server runs on your machine. Nothing is sent anywhere by it. See Security and privacy.
  • When the client gives roots, paths outside them are refused. Files that are not .bpmn, .bpmn20.xml, .dmn or .form files are refused too, and so is a new file made through a link.
  • An assistant can change a diagram only with edit_diagram, layout_diagram, migrate_apply, migrate_agents and the refactor_* tools, make a new file only with create_diagram, import_diagram, generate_templates, incident_to_scenario or evidence_build, none of which replaces a file without being told to, and write an image only with export_image when it passes out. The refactoring tools write only the plan they have just returned: applying needs its planId. run_scenarios writes its traces under .penstock/runs and runs only on an engine marked for tests. Ask the assistant to use dryRun first, and keep your diagrams in Git so you can review the diff. A diagram that changed on disk while an edit was being made is never overwritten: the tool answers The diagram changed while the edit was being made, so it was not written over.

What you see

  • The assistant lists the tools. Paid tools show a note on what they need.
  • A tool call returns JSON, or a plain error message that says what is wrong.

Common problems

The assistant does not see the tools.
Check the command and args in the entry. Node.js 22.22 or later must be on the PATH of the assistant. Run penstock mcp by hand: it should wait silently for input.
"must be an absolute path to a diagram" or "\"project\" must be an absolute path".
The tools take absolute paths. Ask the assistant to pass the full path, as list_diagrams prints it.
"is outside the workspace roots".
The path is not inside a folder the client has open. Open the project in the client, or give a path inside an open folder.
"is not a Penstock project".
The folder has no penstock.yaml and no repository root above it. Run penstock init there.
A paid tool says it needs a licence.
Sign in on the machine that runs the server: penstock license login.
